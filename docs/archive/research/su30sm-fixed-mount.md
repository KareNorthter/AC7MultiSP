## 核心改动边界

先保留当前 `InitializeWeaponSystem` 切换方式、两份弹药和冷却缓存、完整原生选择及 seeker 重绑。增加按机体与实际武器类识别的固定挂载管理，暂不要求两套持久战斗分组。

必须同时管理三个层次：

1. **逻辑槽**：弹药、装填窗口、发射游标和锁定参数仍按原生规则工作。
2. **物理位置**：每个逻辑槽映射到固定位置，实际飞行弹体使用同一位置和方向。
3. **显示模型**：多个槽共用一个显示模型，切换 SP 不改变整组可见性；发射、装填和耗尽改变对应位置的状态。

当前 `restore()` 会把保存的队列从旧游标开始重排到新数组，并将新游标设为零。新增的持久挂点序号必须跟随相同重排：新槽 `i` 对应保存队列中的 `(旧游标+i)%槽数`。不能只按新数组下标固定绑定位置，也不能未经确认复制槽内不透明指针或索引。

显示规则暂定为：位置所对应的槽中仍有分配到实际剩余弹药的就绪弹，则显示一个模型；没有则隐藏；装填完成后再恢复。有限弹药需按队列顺序分配，不能让最后一发同时显示在所有位置。无限弹药的原生 `-1` 状态另行处理。此规则是设计草案，不等于已确认的原生事件实现。

未激活 SP 的装填继续使用游戏时间；暂停不推进。显示更新应接入原生发射/装填事件或确定的装填到期时间，避免每帧强制反隐藏、与原生争抢显隐。所有对象操作保持在游戏线程。

## 原生路径与原型影响

以下地址均为 Steam build 9855922 本轮运行代码的 RVA，仅作研究定位。磁盘 EXE 的已知位置不等于运行代码，本轮通过只读进程采集核对，未调用这些函数。

1. **发射变换**：`0x8997d6` 附近从分组 `+0x68` 索引表取项，调用 `0x8a0960`。后者从 MeshManager `+0xf0` 取活动路由，再读模型组件 `+0x180/+0x190/+0x1a0` 的世界变换；无模型时使用父组件的 Socket 世界变换。另一入口 `0x89cdb0` 还存在缓存变换分支。因此只改槽内 `+0x20` 平移不能保证实际出弹改位。
2. **静态池与路由**：MeshManager `+0x140/+0x150/+0x160/+0x170` 分别保留 MSL、SWP1、SWP2、SWP3 组件池；`+0xf0` 是当前活动路由。`0x8a0a40` 隐藏池中模型并重建路由。`0x8a08b0` 通过组件的挂接父链选择 SP 池，**不是根据可见性选池**；不可为了显示方便破坏原挂接关系。
3. **单枚显隐**：`0x8a0e60` 用槽 `+0x40` 查路由并隐藏；`0x8a1710` 用 `+0x44` 查路由并显示。两者同时维护路由标记和分组显示数量，不能只改组件布尔位。`0x89e3c0` 中还存在推进、改写这两个索引的路径，但本轮单发快照中两字段未变，不能声称每次发射都会推进它们。
4. **延迟恢复**：`0x8a0260` 登记 MeshManager `+0x110` 的队列，`0x8a12f0` 按游戏时间消耗队列。记录引用组号和槽号，不含 SP 身份。`0x89ff10` 的组参数为 -1 时清全部队列并恢复路由状态，指定组时移除该组记录。第四阶段在 `0x81e843` 确认调用 `0x882e40`，闭合 `0x81e810 → 0x882e40 → 0x884f10 → 0x89c530 → 0x89ff10(-1)`。新进程的两片武器代码与前轮逐字节一致。因此不另加清队列逻辑，也不把此前疑问当成现有切换缺陷。
5. **渲染更新**：`0x16f8bc0` 与 `0x16f62b0` 分别处理可见性、游戏内隐藏及子组件传播。直接写显隐位会绕开引擎更新；将多条原生路由简单指向同一模型也会让隐藏事件和数量统计互相干扰。

第一份原型保留原生路由及其计数，在游戏线程中处理固定模型的显示结果和出弹变换。现有弹药/冷却缓存保留，新增物理映射与显示状态管理，不改原生隐藏/恢复索引、不把多条原生路由直接指向同一模型。

## 第三阶段：独立候选的具体实现

候选名 `1.0.2-su30sm-mount.1`，源码为 `src/su30sm_fixed_mount.hpp`，仅通过 `DUALSP_SU30SM_MOUNT_PROTOTYPE` 编译开关接入核心。分支 Lua 新增必需接口 `dualsp_fixed_mount_update`，不能与正式 DLL 混装。当前候选仅在 `Temp/su30sm-candidate.1-build`，没有覆盖 dist 下的任何核心。

- **发射位置**：同时接管直接取位 `0x8a0960` 和选槽取位 `0x89cdb0`。后者先让原生决定槽，再通过活动索引表把结果换成对应固定模型的世界变换，覆盖原生缓存变换分支。重建临时武器池期间保持原生取位，事务完成后启用映射。两个入口的真实发射调用效果仍须实机验证；不声称已覆盖所有辅助瞄准变换。
- **显隐与恢复**：仅过滤当前玩家的三个挂架和十六个原生 SP 模型；普通导弹和其他对象直通。保持原生路由标记、显示数量和恢复队列，由两份逻辑装填窗口聚合六处显示。未激活 SP 按游戏时间推进，暂停不推进。沿用现有 20 ms 游戏线程调度读取状态，仅状态变化才请求引擎更新；不直接写显隐位、不无条件每帧反隐藏。
- **总显隐**：接管 `0x8a11b0` 后补充未激活 SP 的显示，服从 MeshManager 的总开关。第四阶段确认显隐参数 0 不传播，1 仅通知后代渲染，2 遍历后代并以参数 0 调用同一显隐入口。候选 .2 只对参数 2 记录子模型原生状态，并保存共同祖先 RootComponent/WeaponMeshBase 的整组传播请求；固定模型服从该请求，不能把整组隐藏变成武器独自可见。
- **切换连续性**：持久挂点序号随冷却队列一起旋转。现有核心为了让新池生成已装填弹体，会把完成计时写成门槛前一个浮点数。原型只记录这次重建主动产生的门槛状态，将其视为逻辑已就绪，避免切换后模型短暂消失；原生计时仍按既有规则完成事件，不用宽泛误差提前结束真实冷却。
- **身份和退出**：核对 Su-30SM 基类完整资源、实际武器类、模型池数量、Socket、父组件和网格名称；对象表索引与序列号共同防止地址复用。支持 6AAM/LAGM 的两种选择顺序，其他组合使用现有双 SP 行为。解绑、世界切换、功能禁用或错误时归还最后记录的原生显隐；错误明确进入日志和现有 UI，不宣称原型继续正常。

挂架几何依据见[范围摘要](../../../evidence/su30sm-fixed-mount-geometry.json)。两个原版资产的 LOD0 顶点分别为 552、1968，提取位置缓冲后与资源包围盒交叉核对。两者各只有一个 section，不能沿用既有 section 单独关掉翼下或腹部部分；六个横向带的包围盒均有重叠。这是顶点范围研究，不是逐三角面碰撞检测。两套 Socket 也有前后和高低差，单挂架候选是否出现明显悬空必须看实际画面；若不能接受，应制作专用挂架资源，而不是继续叠整套或凭空修偏移。

## 用户实测后的生命周期研究

首轮已由用户确认显示、切换与发射符合预期；日志还显示装填未完成时连续切换后，固定模型就绪掩码由 0 逐步恢复到 63。该日志支持两种 SP 的装填推进和显示恢复，不单独证明六目标锁定齐射或生成瞬间坐标。

| 场景 | 当前依据 | 尚需确认 |
|---|---|---|
| 同一玩家实例的检查点恢复 | `checkpoint_restore` 恢复两份缓存、重定时，再重建持久挂点顺序 | 用户重来后的实际路径、弹药和四加二显示 |
| 整个任务重来或重新创建飞机 | Lua 地址变化先解绑并清空当前配置，再走新 setup | 不能把新任务初始化误记为检查点缓存恢复 |
| 补给保留四加二组合 | `resupply_setup` 重建组合并重新绑定 | 补给期间显隐、起飞后的完整布局 |
| 补给改为其他双 SP | 核心提交时排除不属于原型的武器组合 | 原生单套显示正确归还；初始化开始时的旧接管边界 |
| 补给改为 SP2＝NO WEAPON | 代码审阅发现单 SP 分支不执行核心 setup，也不显式调用固定挂载解绑 | 存在旧接管可能残留的代码缺口，尚无现场复现；正式扩展前必须处理 |
| 检查点从双 SP 回到单 SP | 单 SP 恢复分支也不显式解绑 | 与补给单 SP 的退出所有权问题一并处理 |

后两项是从当前代码路径推导的风险：固定挂载钩子只在世界变化、功能禁用、明确核心事务或错误时释放，而单 SP 恢复后不再运行周期更新。不能依赖“停止更新”自动归还原生显示。建议把新配置应用前的解绑作为明确事务边界，并对单 SP 检查点恢复显式解绑；不要用每帧检测或异常后补救掩盖它。本次只记录研究发现，未修改运行代码或正在验证的候选。

当前优先配合项为暂停菜单的检查点重来。如果自由飞行没有该入口，应记录菜单情况，另用有检查点的任务验证；完整任务重来只能覆盖新任务初始化。后续再验证补给、反向选择、末弹和暂停；不为发现 HUD 剪影异常而扩大本轮修改范围。
