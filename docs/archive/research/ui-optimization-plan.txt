三、PART 悬停增弹与黄色数字

目标行为
光标停在未装备的适用增弹部件上，不按确认，即展示预计载量；只将受影响的数量染黄。
移开、离页、换机或完成装备后，按当前原生状态恢复。武器名称不随数字一起变黄。
MSL 沿用原生数量控件；三 SP 的新数量控件由模组显示同一预览语义。

已经确认
• 当前 main.lua/optionsFor 只查询已装部件后的完整载量。
  src/weapon_bridge.cpp 的 dualsp_loadout_ammo 未给原生计算传入光标候选修正。
• native_loadout.lua 的 PART 每约 250 ms 刷新一次已装结果；克隆的 SP 数字不自动继承源控件后续变色。
  paintColumns 的内容签名主要由武器和数量组成，也不能表达“数字相同但候选影响状态改变”。
• 原生候选读取入口 0x6cf850/0x6cf890；页面持有 HangarStatus，后者关联 BoardWeaponsAmmo。
  原生弹药绘制入口 0x6efd90；上下文访问链 0x8df100 → 0x8df120。
• 0x84e050 累计已装部件，0x84e770 按单个 PartsID 累计候选修正；0x84dc40 根据真实 WeaponID
  合并修正，包含原生截断及部分武器类别的偶数规则。候选已在上下文部件列表时，不能再次叠加。
• 原生着色取 TextColorStandard、TextColorOnCursor、TextGlowOnCursor。
  有候选影响时关闭全局泛光继承，设置候选颜色和局部泛光；无影响时恢复标准样式。
  本机读到的候选泛光值为 (0,0,0,0.2)，不能把它描述为已确认的强黄色发光或闪烁。
• 0x84dc40 的影响标记表示候选修正适用于当前武器，不等同于“最终显示整数变大”。
  均分取整后数量相同，也可能仍需按原生规则变黄。数字不额外加入性能条的闪烁动画。

实施步骤
1. 在核心新增专用只读预览查询。建议输入当前 PART 页面及所选机体身份，输出同一时刻的：
   页面/世界/机体代次、候选 PartsID、预览模式、已装列表身份，以及每个 SP 的当前完整载量、
   候选完整载量和 candidate_affects。字段名可调整，语义须明确。
2. 在原生 PART 更新完成后捕获一致快照，先核实回调顺序；若使用轮询，只访问已绑定页面。
   不能混用上一光标候选与下一光标的部件列表，不能以全局候选镜像作为唯一依据。
3. 每种 SP 使用实际 WeaponClass 默认对象的 WeaponID，不以菜单 PWDT 序号代替。
   当前值和预览值分别从基础完整载量开始计算，避免把已含部件的数量再次加成。
4. 最后使用 loadout_profile.lua/Profile.ammo 按真实搭载数 1/2/3 均分。
   EMPTY 不计入分母；MSL 不均分。候选部件不改变 SP 方案、槽数或任务弹药。
   示例仅用于说明顺序：完整载量 68，适用候选加 8，则三挂为 22→25，双挂 34→38，单挂 68→76。
5. main.lua 将只读快照交给 native_loadout.lua；普通已装刷新与候选刷新合并为同一显示入口。
   更新签名加入候选身份、影响标记及样式状态，避免下一次 250 ms 刷新又把黄色数字覆盖回去。
6. 只更新 SP 数字；保存并恢复其标准颜色和泛光策略。MSL 优先保留原生所有权，不新增第二个写入者。
   确认装备交给原生处理，随后读取新已装结果并清除候选状态。

实施前必须补齐的证据
之前悬停 107 号 Take off weight augmentation (SP.W) Lv.1 时模组开启，原生 SP 源控件受到接管，
没有完成“模组关闭”的原生 A/B。不能把该记录写成已完整验证原生黄字效果。
仍需核实 MSL 悬停、已装部件重悬停、同组替换、卸件、满槽/超容量和不可装时的上下文。
尤其不能把替换/卸件一律算成“全部已装 A 加候选 B”。不得通过临时装上再卸下来获取预览。

验收重点（后续实施后执行）
单/双/三 SP、适用与不适用武器、取整后数字不变、快速移光标和退出恢复；确认前配置/任务数据不变。
MSL 黄字正常且不影响 SP；只读候选样式不会带入 STANDBY、补给或飞行 HUD。

四、武器性能条：绿色增量与黄色闪烁

目标与当前缺口
机库保留透明未填充区、原生立体边框和蓝色基础值；绿色表示已装部件增加的部分，
PART 页黄色闪烁表示当前候选带来的预览差值。选装、STANDBY、补给至少显示已装后的正确结果。
补给沿用其原生页面配色，不直接把机库蓝色强套到补给绿色界面。

当前 performanceBar 只创建 BarA 和底/左/右边框；paintColumns 读取 PWDT 基础 stats。
已有透明底和边框不是完整三段性能条。options.max 含弹药加成，也不意味着 options.stats 含图表加成。
原生 PartsDataTable 有独立 GraphAirToAirWeapon、GraphAirToGroundWeapon、GraphHoming、
GraphLongRange、GraphDamageRange、GraphReload。107 号部件的“载量 +8”与“空/地性能图表 +5”
就是不同数值。不能用弹药百分比推算绿色长度，也不能把原生当前单 SP 的条宽复制给全部 SP。

数据实施
1. 沿用第三节的页面/候选快照，但单独研究原生图表计算与武器适用分类。
   检查实际加载的部件图表、覆盖字段及其调用链；尚不能认定直接累加六个 Graph 字段就等价于原生。
2. 为每槽六项输出 base、installed、preview 和预览有效状态；三者定义为同一量纲的累计端点。
   图表数据按当前武器类别、已装与候选状态计算；弹药均分不应直接按 1/N 缩短性能条。
3. 核实原生上限、溢出、同组替换和负向差值显示。正向示意：
   蓝段 [0, base]，绿段 [base, installed]，黄段 [installed, preview]。
   这只是正向加成的绘制定义；负向/替换必须按核实后的原生语义另行处理，不能伪造正向黄段。
4. paintColumns 的差异判断加入六项数据与预览代次。
   当前只比较“武器+弹药”会漏掉不增弹、但改变射程/追踪等性能的部件。
   保持现有 statOrder 映射，特别注意装填、范围、伤害范围在目录与画面中的不同顺序。

绘制与动画实施
• 扩展 performanceBar，一次创建并缓存 A/B/C 叶控件和原生边框，分别复用原画刷、透明度与泛光。
  不铺满背景、不重复乘蓝色、不按横向宽度缩放边框线厚。无增量/EMPTY 时隐藏相应填充。
• 已确认 BlinkBarC 周期 1 秒：0/0.5/1 秒透明度 1/0/1，三次插值，持续循环。
  复制 BarC 叶控件不会自动复制原 UserWidget 的动画绑定，不能只调用一个同名动画便假定有效。
• 推荐保留现有叶控件构造方式，用当前可见 PART 页的一套时间源驱动所有有效黄段。
  从资源读取/核对插值切线后复现曲线；若采用近似曲线，应明确记录视觉近似，不能声称完全一致。
  只有证实原生 UserWidget 构造、绑定及释放可靠后，才考虑直接复用完整动画控件。
• 数据仅在候选/配装变化时重新计算，动画帧只改变缓存 BarC 的透明度。
  没有有效黄段、页面隐藏或已离页时停止动画更新；不在动画中查表、扫对象、重建控件或写日志。
• 若帧率或暂停影响曲线，应先明确使用哪种 UI 时间与暂停语义，再与原生对照；不为每条黄段创建独立定时器。

验收重点
六项映射正确，只有适用 SP 出现绿/黄段；安装后黄色转为当前已装结果，移开恢复；
到达上限不会越框，零值不留亮线，EMPTY 无虚构增量；不同页面边框和配色保持一致的原生风格。

五、选择机体后进入 SP1 的偶发停顿

先区分现象
A. 画面仍流畅，但 SP1 等待机体模型/兵装组件就绪：属于加载延迟或接入发现延迟。
B. 背景动画、输入或整帧短暂冻结：可能有游戏线程上的集中工作，需要帧时间证据。
二者可能同时存在。单凭用户描述或 PERF_TICK 不能确定是哪一种。

当前源码链路
main.lua/optionsFor 从 HangarManager.LoadedPlayerPlane 读取实际预览实例，核对选择编号、类继承、
世界和兵装组件后，读取三个 WeaponID、载量、购买状态，组成选项。
模型尚未跟上选择时返回显式等待原因；native_loadout.lua/modelChoices 显示受控等待，
暂停选装确认，保留 10 秒超时和明确错误，模型就绪后接入三栏。
页面 SetIsEnableControl 激活事件已直接传入 owner；通常无需等待全局发现。
非补给全局页面发现间隔约 500 ms；可见性/接入扫描还有约 50 ms 的节流，主调度间隔 20 ms。
这些间隔不是无条件累加的固定延迟。需查看具体一轮是否漏过激活事件、走到发现路径。
当前三栏创建包含 18 个性能条，各条还创建多幅图像；增加 B/C 后同步创建成本会继续增加。
这是应测量的候选热点，不是已经确定的卡顿原因。

先测量，再决定改哪里
建议在后续实施中加入一次换机一条的分段摘要，携带同一页面/机体代次：
T0 选择变化；T1 原生页面激活；T2 模型和兵装身份就绪；
T3 optionsFor 完成；T4 新控件与首次绘制完成；T5 SP1 恢复可操作。
分别记录模型等待时间、发现滞后、选项查询、控件创建、首次绘制和总交接时间。
T4 只能表示代码提交完成，不能冒充 GPU 首帧呈现时间；帧冻结另用帧时间记录或录像对照。
现有每 15 秒 PERF_TICK 只统计主 Lua 回调，不完整覆盖事件钩子、原生资源加载或整帧成本。
分段计时宜用核实过的单调时钟/原生高精度计时，不能未经确认就把 CPU 时间当作墙钟等待。
记录汇总和慢样本即可，不逐控件/逐帧落盘，以免测量本身制造停顿。

依据结果选择优化
1. 若主要是模型加载：保留身份检查和受控等待，核对是否有已加载的有效实例可直接使用。
   不取消检查、不拿上一架机体抢先展示，不为预览主动重建或初始化武器系统。
2. 若主要是发现滞后：让已知 owner 与等待代次继续直达后续检查，缩小对全局发现的依赖。
   先核实激活事件与 planeId 更新顺序；不能把所有页面扫描改成每帧来掩盖时序问题。
3. 若主要是选项查询：消除同一代次重复的类链/静态数据查询；将语言名称、模板等稳定数据与
   已装部件、购买状态、候选预览分开缓存。换机、换世界、页面重建、语言/部件变化时按依赖失效。
   同次查询中重复 isSelectedPlane 核对可评估合并，但提交边界的安全校验仍需保留。
4. 若主要是控件创建：优先减少重复创建及重复样式设置，复用同一有效 owner 下的自身控件。
   不跨世界保留 UObject，不浅复制带 Slots 的父容器，不缓存旧预览机体。
   仅在实测仍有明显集中耗时后考虑分帧构建：在游戏线程分批创建隐藏子树，完成后一次显示，
   期间保持受控等待；取消/换机必须归还控件和输入。不能出现逐栏拼装、原生单 SP 闪现。
5. 若摘要显示日志/状态发布占比显著：减少未变化内容的序列化与落盘，保留重要状态及错误。
   不吞错，不仅通过关闭日志让问题难以观测。

验收与记录方法
在相同环境记录冷换机、热换机、快速连续换机、第三方机体、返回后重进；建议每类至少 10 次。
报告分段耗时、最大停顿及样本数，样本足够时再给分位数；不只报平均值。
没有基线前不承诺“提升百分之多少”。实测应确认模组自身同步耗时下降，且错误机体、旧候选、
输入锁残留、超时和单 SP 闪现没有回归。原生资源加载耗时单列，不算作模组已经消除的成本。

当前布局源的右栏 X≈1442、宽≈374，左侧内容右界约 1417；间隙约 25 个逻辑像素。
右移 32 后，右栏起点约 1474、右界约 1848，间隙约 57，1920 宽基准下右侧仍余约 72。
以上是当前原生布局基准下的估算；2560×1440 等比呈现时，右移量约 43 个屏幕像素。
保持字体、卡片宽度、条长和纵向间距，避免通过缩小字体换取留白。
实际修改仍从当前 Canvas 槽读取位置，核对父容器/安全区和尺寸，不硬写截图像素坐标。

关键实现注意
native_loadout.lua/attachStandby 目前还用 origin.X 参与弹药块左移计算：
  ammoPosition.X + leftOrigin.X - origin.X
直接在该 origin 上加 32，会让弹药块再向左移动 32，破坏已经调整好的左侧对齐。
应明确分成两个位置：nativeRightOrigin 保存原生定位基准；spCardOrigin 单独加右移量。
只用 spCardOrigin 创建三个卡片；弹药仍使用 nativeRightOrigin 与 leftOrigin 计算。
保持 repositioned 的原布局恢复机制，避免重复进入时累计平移。

左侧机体与弹药不移动，右侧文字/条形不裁切，退出返回不累计偏移。
超宽屏等布局若不同，按实际有效画面和父容器校正，不靠越界后静默缩字。

位置定义
按“从屏幕中点朝顶端移动这段距离的 2/5，位置更靠近中点”解释：
  中心高度 0.5H；上移 (0.5H × 2/5)=0.2H；最终中心 Y=0.3H。
  水平中心 X=0.5W。
1920×1080 对应中心 (960,324)，2560×1440 对应 (1280,432)。
这里定义的是包含文字的方框中心，不是文字基线，也不是“从屏幕顶端算 2/5”。
有黑边或独立有效视口时，以游戏 HUD 所属有效画面为基准。

update 按实际活动武器更新简称，字体现按原生 11/9 放大，绿色 (.08,1,.05)，正常 Alpha .7，
未就绪时乘 .35，并共享现有武器就绪状态。

建议控件结构
在原生 HUD 所属 Canvas 下建立本模块自己的透明容器：
  CurrentWeaponPanel
    四条 Image 边线（上、下、左、右）
    当前武器简称 TextBlock
此处需要完整四边框，与性能条的三边框不同。不使用有底色的背景块。
容器和子控件不拦截输入；原瞬时面板仍按已有 holder 机制隔离，不挪动整个原生 HUD。

定位与尺寸
先核实 sourceParent 是否覆盖整个有效 HUD 画面；若是，固定锚点设为 (0.5,0.3)，
容器 alignment=(0.5,0.5)，offset=(0,0)。若不是，用有效画面的目标点换算至该父容器局部坐标。
不要把 1920×1080 的物理像素直接写进受 DPI 缩放的 Canvas，也不能盲沿用原生 Y 偏移。
建议初始内边距：水平每边 10、垂直每边 5 个逻辑像素；线厚 1 个逻辑像素。
使用当前机体 MSL/各 SP 最长简称和实际字体的测量宽度确定框宽，保持同一机体切换时框宽稳定；
字号/语言/分辨率或 HUD 重建时重新测量。尺寸须在布局有效后读取，不能用未布局的零值或字符数猜宽。
框高按实际文字测量高度加上下内边距。测量 API 是否可用，应在实施前与现有 preflight 一并核对。

颜色、泛光与生命周期
边线复用文字同一 RGB、基础透明度与就绪系数，未就绪时文字和框一起变淡。
可沿用经过核实的局部泛光接口；先保证细线清楚、不压住文字，不叠加强烈光晕。
现有环境没有确认可用的 Widget:SetRenderOpacity，不以该 API 作为方案前提。
框只创建一次，计入 c.added；切换武器只改内容/状态，不重建框或再次扫描 HUD。
reset/restore/fail 同步清理容器和边线，归还原面板；补给、检查点及世界变化继续重新绑定。
真正接入失败仍明确报告，恢复原生提示是错误处理，不用空框伪装成功。

“始终开启”的具体落实
含义：模组正常启用的任务 HUD 内固定显示，不给用户独立关闭选项。
仍遵守游戏整体 HUD 显隐、过场/菜单/补给生命周期及模组适用模式，不在原本无 HUD 的画面强行叠字。

  建议将这次必需字段变化作为下一协议版本（实施时核实版本是否仍为 3），同步更新 Lua/UI 和兼容检查。
  迁移旧配置时一次备份并移除废弃偏好；旧 central_hint=false 也变为固定开启。
