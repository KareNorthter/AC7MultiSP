TLS 与 ECM 持续效果：当前架构可行性研究
2026-10-15；独立分支 codex/aircraft-mount-survey；研究基线 af4ce5d。

一、结论与本轮边界

用户说明原版 TLS 发射后切到 MSL，光束会继续随飞机发射；本模组为避免切换 SP 后光束留在原地，主动结束 TLS。原版行为在此作为用户观察记录，本轮没有重新实机对照。
用户追加范围：如需大改底层架构，TLS 问题不要求现在解决。因此分成两个独立目标，不以跨 SP 全部解决作为局部改善的前提：
（1）TLS → MSL：当前流程不重建 SP，有局部修正的明确候选；仍须实际发射对照后才能部署。
（2）TLS → 另一 SP：已发现原生活动登记被清空、结束回调访问当前 SP 的冲突；不建议现在删除强制收尾。保留现状，将完整持续效果支持后置。
（3）ECM：资源证实有持续状态，但没有类似故障的本轮实测。实际 ECM 仍仅支持单挂，本轮不放开限制。
没有修改运行源码、编译、安装、启动游戏、调用游戏函数、写入游戏内存或运行测试模块。现有 Su-30SM 三 SP 候选保持原样；不处理 HUD 剪影问题。

二、源码确认的两条路径

dist/DualSP/Scripts/main.lua 的 selectLogicalWeapon：
  只要目标不是当前逻辑 SP，且当前挂载的实际 WeaponID 为 25，就调用 finishTLS。
  仅当目标为另一逻辑 SP，才释放发射输入并执行 native("switch", target)。
  目标为 MSL 时仅通过飞机原生切换入口改变类别，保留当前 SP 配置及池。
因此 TLS → MSL 的主动关闭范围比兵装重建范围更大。当前 MSL 保留上一 SP 的设计使小范围改善成为可能；不是保证取消调用后一定正常。

小改候选：只在“实际将重建另一 SP”之前结束 TLS，直接切到 MSL 时不主动终止。必须按最终逻辑目标判断，不能只检查原生 armed 状态，因为原切换键可能先变成 MSL，再由模组选择下一 SP。
TLS → MSL → 原 TLS 应一直不重建；TLS → MSL → 另一 SP 则仍要在重建前收尾。结束调用必须在旧槽冷却快照之前，不能改变现有事务顺序。
这一候选主要是 Lua 决策边界调整，不要求先重写多 SP 核心。对外部 TLS 变体、最后一发、按键连切、自然结束和原切换键循环仍需验证。本轮不修改这条运行逻辑。

src/weapon_bridge.cpp 的 execute("switch")：
  捕获当前 MSL/SP 数值 → initialize 新配置 → 恢复 MSL 和目标 SP → 更新逻辑活动槽 → 恢复武器类别。
Group 缓存包含武器类、0x20 标量、各槽装填时长/进度和捕获时间；固定挂载候选另保存挂点序号。它不是持续发射对象的完整生命周期缓存，没有保存 TLS Actor、附着关系、活动登记、效果计时或源槽回调归属。
Su-30SM 固定挂载解决的是模型呈现和离架位置，不能据此认为活动 TLS 或 ECM 已经获得持续运行支持。

三、TLS 资源与原生旁证

原版 plwp_tls_x0/x1/x2/x3 均直接继承 AttachedInstantWeapon，明确设置 bIsBaseAttached=true、LifeTime=8、bSwitchWeaponOnLastDestroyed=true。x2 的 LoadTime=11，其余三个为 13；这是未计部件及第三方覆盖的资源值，不作为现场承诺。bReloadOnFire 等未序列化字段仍属原生默认未知。
历史实际玩家 x2 的反射已确认 AttachedInstantWeapon → AttachedWeapon → WeaponBase。AttachedWeapon 有 bIsBaseAttached(+0x638)、AttachedComponent(+0x640)、AttachedSocketName(+0x648)。它与普通导弹的脱离飞行机制不同。
历史 Tick：0x85f470 → 0x8614c0 → 0x8980e0；附着武器基类检查所属机体有效性/健康，失去所属机体则进入 0x894af0 自然结束请求。不能拿默认 LaserWeapon 的不同 Tick 当作玩家 TLS 的必要条件。

本轮重新读取已有、带哈希的原生代码快照，确认三个关键结构冲突：
1. initialize 使用 0x81e810 → 0x882e40；0x88388e 调用 0x884f10。在 0x884fa5/0x884faf，原生把 activator+0x338 的 ActiveWeapons 数量置零。仅停止主动关光束，不能让旧效果自动保留正确登记。
2. 0x89da40 → 0x89bc40 清理原武器组的多个动态数组，再建立新的组。不能把旧池/槽指针保存下来，当作仍有效的持续上下文。
3. TLS 自然收尾链 0x894850 → 0x885240 会移除活动对象；该回调随后访问 owner+0xf0 对应当前状态中的 SP 默认对象和弹药。TLS 资源又明确启用“最后销毁时切换武器”。旧 TLS 结束时存在干扰新 SP 状态/选择事件的结构风险，不应只修视觉。
另有通用结束路径 0x897010，按武器内保存的 owner/group/slot 信息调用 0x89e3c0；后者由 group 编号从当前 owner 状态定位槽并推进装填。该路径受原生标志约束，本轮没有确认每种 TLS/ECM 的实际触发分支，不能声称已经复现串槽冷却。

“激光留在原地”是用户历史观察；现有证据还不能唯一认定为解除附着、父组件停止更新、池对象复用或其他原因。不得把 ActiveWeapons 清空直接等同于已证明的定点光束根因，也不靠每帧把光束搬到机头掩盖问题。
磁盘 EXE 在所检查 TLS Tick 入口的字节与历史运行内存不同，原因未判定；已停止从磁盘入口继续推导。上述原生结论来自历史运行内存和反射，不能冒充本轮活动光束现场。

四、跨 SP 完整支持为何暂缓

有条件可行的方向：让已发射的持续效果保留原生 Actor、有效附着和自己的寿命；按“飞机身份＋逻辑源槽＋发射代次”记录归属，保证活动登记、结束通知和装填更新仍回到原槽，当前选择只决定下一次发射。
需要同时确认并处理原生池清理、引用有效性、Tick/伤害更新、音效、结束回调、最后一发自动选择，以及检查点/补给/死亡/换世界清理。不能复制一束新激光重开计时，也不能只加回 ActiveWeapons 或屏蔽全部结束回调。
若必须让各 SP 拥有常驻原生兵装组才能满足这些条件，就涉及核心生命周期设计，连带锁定组件、部件效果和原生事件；按用户最新要求留待后续，不作为本阶段工作。
共享弹仓动画与持续武器对象是两个不同问题：它们都需要明确归属，但不能把弹仓不重播的实现当成 TLS 持续发射的解决方案。

五、ECM 风险核查

plwp_ecmp_x1/x2 → plwp_esm_x0 → ElectronicSupportMeasures，实际 WeaponID 为 ECM（现有代码按编号 31 限制）。其基类名称带 Support，不代表只有支援效果，也不能把菜单上写 ECM 的第三方替换武器当成真实 ECM。
父资源明确有 EffectRangeMeter=3200、JammingTimeCampaign=26、SupportTimeCampaign=26、LifeTime=30、LoadTime=42，并有作用武器名单、干扰参数和支援参数。bJammingEnable/bSupportEnable 本批未显式序列化，未读取原生缺省，不能因两套参数存在就断言两种作用同时启用。
历史反射还显示机体持有 JammingMeasures/SupportMeasures 引用；ECM 类有后处理、有效范围、优先级、叠加及效果时间字段。效果存在至少“发射对象”和“受影响对象”两个核查层次；对象寿命、实际作用时长和装填时间不能互相代替。

当前实际 ECM 仅单挂，ECM ↔ MSL 没有跨 SP 重建，也不会触发 WeaponID=25 的 TLS 结束接口。从代码看，不处于已确认的跨 SP 重建风险路径；这不等于已实测所有 ECM 边界。
若未来放开 ECM 多挂，要关注：作用范围中心是否随飞机移动、目标干扰/增益是否保留并按时撤除、切回是否重复施加、优先级/叠加是否正确、实际冷却是否计入效果持续阶段、旧结束事件是否干扰新 SP。
可能表现为特效还在但实际失效，或者特效消失而目标效果未撤销，不一定像 TLS 那样有明显“停在原地”的光束。当前没有发生这些问题的证据，均为需要验证的风险。

六、后续最小验证，不要求用户现在操作

优先只验证 TLS → MSL 局部候选：原版/现状/候选保持同一机型及模组环境，发射后转弯再切 MSL，观察跟随、伤害、自然结束、弹药、冷却和最后一发行为；同时覆盖直接选择与原切换键。当前安装有第三方 TLS 参数修改，不能把候选与不同配置的原版混作对照。
补充只读采集：活动 TLS 的身份/池状态、附着父组件/挂点、效果剩余时间、源槽、ActiveWeapons 以及自然收尾前后值；先取得活动样本，再判断跨 SP 是否存在局部解法。
ECM 先维持原生单挂与 MSL 切换，验证干扰确实随飞机、在设定时间撤除；随后再决定是否值得继续。代理不自动出击或发射，本轮游戏保持关闭。
证据：evidence/continuous-sp-effects-research.json。已有强制结束实现和 ECM 多挂限制均保持原样。
