## 固定分配

编号使用原生 Socket，避免把用户示意编号误当成资源编号。`sp11/sp12` 与 `sp13/sp14` 分别是两对翼下位置，`sp35/sp36` 是 LAGM 原生靠中线的低位一对；左右以现场画面最终核对。

| 武器 | 原生逻辑槽 | 目标物理位置 | 显示 |
|---|---|---|---|
| 6AAM | sp11、sp12 | sp11、sp12 | 每处一个模型 |
| 6AAM | sp13、sp14 | sp13、sp14 | 每处一个模型 |
| 6AAM | sp15、sp16 | sp13、sp14 | 共用前一行的两个模型，不额外叠放模型 |
| LAGM | sp31、sp33、sp35 | sp35 | 共用一个模型 |
| LAGM | sp32、sp34、sp36 | sp36 | 共用一个模型 |

6AAM 六个逻辑槽与六枚装填窗口保留；满装六发时四处的出弹数分别为 1、1、2、2。LAGM 保留六槽、两枚装填窗口的资源配置，任意连续两槽按本方案都落在两处不同位置；本轮现场已确认这两种窗口配置。普通导弹继续使用自己的 `ws1/ws2`。

位置、旋转沿用对应原生 Socket，不把 LAGM 随意挪到 QAAM 外翼位置。此分配仅确定导弹模型的候选布局。两套完整挂架网格可能还含未使用位置的结构，不能直接把两套网格全部显示就宣称完成；需要检查能否共用一套挂架并单独挂接六个显示模型。

## 核心改动边界

先保留当前 `InitializeWeaponSystem` 切换方式、两份弹药和冷却缓存、完整原生选择及 seeker 重绑。增加按机体与实际武器类识别的固定挂载管理，暂不要求两套持久战斗分组。

必须同时管理三个层次：

1. **逻辑槽**：弹药、装填窗口、发射游标和锁定参数仍按原生规则工作。
2. **物理位置**：每个逻辑槽映射到固定位置，实际飞行弹体使用同一位置和方向。
3. **显示模型**：多个槽共用一个显示模型，切换 SP 不改变整组可见性；发射、装填和耗尽改变对应位置的状态。

当前 `restore()` 会把保存的队列从旧游标开始重排到新数组，并将新游标设为零。新增的持久挂点序号必须跟随相同重排：新槽 `i` 对应保存队列中的 `(旧游标+i)%槽数`。不能只按新数组下标固定绑定位置，也不能未经确认复制槽内不透明指针或索引。

显示规则暂定为：位置所对应的槽中仍有分配到实际剩余弹药的就绪弹，则显示一个模型；没有则隐藏；装填完成后再恢复。有限弹药需按队列顺序分配，不能让最后一发同时显示在所有位置。无限弹药的原生 `-1` 状态另行处理。此规则是设计草案，不等于已确认的原生事件实现。

未激活 SP 的装填继续使用游戏时间；暂停不推进。显示更新应接入原生发射/装填事件或确定的装填到期时间，避免每帧强制反隐藏、与原生争抢显隐。所有对象操作保持在游戏线程。

## 当前现场结果

本轮为当前已安装的 1.0.1 兼容环境，Su-30SM s03，同一任务，配弹比例 100%，不是默认 50%。未安装固定挂载原型。

| 阶段 | 原生逻辑状态 | 模型与飞行弹体 |
|---|---|---|
| 切至 6AAM | 六槽、六枚窗口、68 发，游标 0 | 当前路由绑定 SWP1 的六个模型 |
| 6AAM 无锁定单发 | 68→67，游标 1，首槽装填计时约 1.338 秒 | 首个模型隐藏，生成独立 `plwp_6aam_r0_C` |
| 切至 LAGM | 六槽、两枚窗口、28 发，活动索引表 `[0,1]` | 当前路由绑定 SWP3 的六个模型，六个均可见 |
| LAGM 单发 | 28→27，游标 1，活动索引表 `[2,1]`，槽 2 计时约 1.909 秒 | 路由 0 隐藏；恢复队列登记组 2、槽 0、剩余约 8.091 秒；生成独立 `plwp_lagm_r0_C` |
| LAGM 装填后 | 仍为 27 发，索引表 `[2,1]`，槽 2 就绪 | 路由 0 恢复，恢复队列为空，活动弹体登记为空 |

切换和发射期间，三个挂架、16 个 SP 模型和两个普通导弹模型，共 21 个组件的地址、对象表索引与序列号保持相同。不能把活动路由重建误认为静态组件销毁。

6AAM 静态挂载和飞行弹体均使用 `w_4aam_r0_SM`；LAGM 均使用 `w_lasm_r0_SM`。这是本次实际加载的原生资源命名，不是选错武器。飞行 Actor 的 Owner 是玩家，根组件不挂接飞机；不是把静态组件直接扔出去。

本轮只观察各一发，未验证六目标齐射或 LAGM 完整六槽循环。快照在离架之后，不能用飞行弹体此时的位置冒充生成瞬间位置。LAGM 恢复的是旧位置的模型，而就绪弹已轮转至新槽；模型可见与槽就绪不能直接等同。

## 原生路径与原型影响

以下地址均为 Steam build 9855922 本轮运行代码的 RVA，仅作研究定位。磁盘 EXE 的已知位置不等于运行代码，本轮通过只读进程采集核对，未调用这些函数。

1. **发射变换**：`0x8997d6` 附近从分组 `+0x68` 索引表取项，调用 `0x8a0960`。后者从 MeshManager `+0xf0` 取活动路由，再读模型组件 `+0x180/+0x190/+0x1a0` 的世界变换；无模型时使用父组件的 Socket 世界变换。另一入口 `0x89cdb0` 还存在缓存变换分支。因此只改槽内 `+0x20` 平移不能保证实际出弹改位。
2. **静态池与路由**：MeshManager `+0x140/+0x150/+0x160/+0x170` 分别保留 MSL、SWP1、SWP2、SWP3 组件池；`+0xf0` 是当前活动路由。`0x8a0a40` 隐藏池中模型并重建路由。`0x8a08b0` 通过组件的挂接父链选择 SP 池，**不是根据可见性选池**；不可为了显示方便破坏原挂接关系。
3. **单枚显隐**：`0x8a0e60` 用槽 `+0x40` 查路由并隐藏；`0x8a1710` 用 `+0x44` 查路由并显示。两者同时维护路由标记和分组显示数量，不能只改组件布尔位。`0x89e3c0` 中还存在推进、改写这两个索引的路径，但本轮单发快照中两字段未变，不能声称每次发射都会推进它们。
4. **延迟恢复**：`0x8a0260` 登记 MeshManager `+0x110` 的队列，`0x8a12f0` 按游戏时间消耗队列。记录引用组号和槽号，不含 SP 身份。本轮 LAGM 发射、装填两份快照与该结构相符。已读重建函数未见清理此队列，仍须检查调用者，不能据此认定现有切换存在缺陷。
5. **渲染更新**：`0x16f8bc0` 与 `0x16f62b0` 分别处理可见性、游戏内隐藏及子组件传播。直接写显隐位会绕开引擎更新；将多条原生路由简单指向同一模型也会让隐藏事件和数量统计互相干扰。

原型应在一次游戏线程操作内协调路由、固定模型和重建后的状态。发射位置重定向与固定显示可复用已有静态组件，但接入方式尚未选定；不采用每帧反隐藏。现有弹药/冷却缓存可保留，新增的是物理映射与显示状态管理。

## 原型实施门槛

发射变换与显隐入口已有依据，仍需完成三个接入问题：覆盖实际使用的变换路径；在重建和延迟恢复期间统一管理共享模型显隐；确认两套挂架能否保留原挂接关系而呈现要求的布局。之后编写最小原型。原型仅针对已核对的 Su-30SM 与 6AAM/LAGM 组合，不按机体编号套用于第三方新增机体；结构不匹配要明确拒绝启用该原型，不静默套用近似布局。

第一阶段观察四处加两处模型与切换连续性；第二阶段由用户验证六发出弹、LAGM 轮转和装填；之后覆盖射后立即切换、剩余弹药不足、暂停、部件、补给与检查点。候选核心单独构建，不能覆盖正式核心。安装前还需重新核对正在进行的第三方兼容工作及已安装文件，防止使用研究快照回退它们的新改动。

本阶段执行只读现场采集、研究数据分析与 Python 语法解析，未修改运行功能、编译核心、新增或运行测试模块，也未安装、启动或停止游戏。当前不再需要用户重复进行原生发射操作；下一次实机配合应针对原型的具体改位与显示效果。
