# 武器名称半透明：可行性评估

评估日期：2026-10-13。返回[项目入口](../../AGENTS.md)；相关资料见[架构](../architecture.md)、[武器核心研究](core-findings.md)和[补给候选](../native-resupply.md)。

后续状态：用户已要求实现并安装，本功能已加入[补给/HUD 合并候选](../hud-candidate.md)。下文保留本轮实现前的评估依据；当前实现与安装状态以合并候选说明及安装记录为准。

兼容性更正：用户实玩日志证实 AC7 当前引擎不提供 `Widget:SetRenderOpacity`。最初按较新 UE 文档作出的接口判断不适用。候选 2 使用固定克隆名称的文字/阴影颜色 Alpha，并修复出击与补给的共用遮蔽机制；不是寻找不存在接口时的静默回退。

## 结论与范围

可行，与当前固定 SP1/SP2 行的 HUD 结构兼容。绘制修改小，主要工作是提供可靠的装填就绪状态，并处理未激活 SP、武器重建及任务生命周期。按下述方式实现，预计性能影响很小；本轮没有实现、编译、运行测试或启动游戏，不能给出实测帧率结论。

本轮只评估 MSL、SP1、SP2 的名称，不改变弹药数字、选择箭头、GUN、FLR、DMG。用户图片只作为显示需求参考，不据此推断 AC8 的实际装填规则。

| 状态 | 名称显示 |
|---|---|
| 剩余弹药为 0 | 半透明 |
| 剩余弹药大于 0，但没有一发就绪 | 半透明 |
| 剩余弹药大于 0，至少一发就绪 | 恢复原来的正常文字 |

“某个槽正在装填”不能直接作为变暗条件：例如双发 MSL 发射一枚后，另一枚仍可用，名称应保持正常。未锁定目标、没有选择该武器、机体暂时禁止输入，也不应被混同为装填未完成。

## 当前代码与证据

1. `dist/DualSP/Scripts/native_hud.lua` 在原生 `CombinedStatsWidget_C` 中创建固定的两条 SP 名称和计数行。原生当前 SP 控件保留在折叠父容器内，切换时不交换可见行身份。这是当前防闪烁方案的基础，应继续保留。
2. 同文件每次更新都会从隐藏的原生名称、计数控件复制 `ColorAndOpacity`。若在别处单独修改文字颜色的 Alpha，下一次更新可能覆盖它。应在现有 HUD 模块内统一处理透明度。
3. [HUD 结构摘要](../../evidence/native-hud-layout.json) 已定位 MSL 的 `MainWeaponTextBP`。当前 HUD 必需控件列表尚未包含它，接入该功能时需加入检查和恢复管理。
4. 最初的 `native_loadout.lua` 引用了 `/Script/UMG.Widget:SetRenderOpacity`；用户实玩日志已证实该引用错误。源码中存在调用不能证明引擎提供接口，较新 UE 文档也不能替代当前游戏反射证据。修复后的准备页使用折叠容器保留源控件，HUD 使用 `TextBlock:SetColorAndOpacity` 与 `SetShadowColorAndOpacity`。
5. `main.lua` 每 100 毫秒通过原生 getter 更新 MSL 和当前 SP 的剩余弹药。周期更新会清空 `nativeState.slots`、`nativeState.reload`；未激活 SP 的计数只在切换、补给、检查点等事务中刷新。因此现有周期数据不足以直接支持装填提示。
6. `src/weapon_bridge.cpp` 已捕获 MSL、两组 SP 的计时槽、逻辑队列游标、装填窗口和捕获时刻。现有 `slots` 输出只提供两组 SP 的进度，MSL 未输出同类就绪字段。它通过命令/状态文件交付，不适合直接升级为持续高频完整快照。
7. `src/reload_timer.hpp` 和[历史原生函数体](../../evidence/native/)支持按游戏时间推进未激活 SP 的冷却。`loadedCount` 用于限定装填窗口，不能直接解释为当前已完成装填的数量。它与队列游标、各槽计时必须一起判断。

## 建议实现

### 显示层

保持原生颜色同步，在独立克隆名称的颜色 Alpha 上叠加状态系数，并同步阴影 Alpha。无就绪弹时乘以 0.5，恢复时使用原生正常值，不能硬设为 1。资源摘要中的文字颜色 Alpha 已是 0.5，直接指定同一个绝对值可能看不出变化。

仅修改 MSL 和单/双 SP 的克隆名称，不修改整行或父容器透明度。数字、箭头和原生字体缩放保留现有行为，文字阴影一起变淡。仅在目标颜色变化时调用设置接口。

MSL 原名称也属于游戏直接管理的控件，候选 2 将其与 SP 来源一起保留在折叠容器，使用固定克隆显示，避免原生更新覆盖状态颜色。不能因为接入失败就静默保持正常并宣称功能成功；沿用明确的 HUD 错误记录与 F8 原因显示。

关闭模组 HUD、错误恢复、检查点、补给返回、机体或世界变化时，保存值与就绪状态应同步恢复或丢弃，防止旧机体状态残留。当前 `restore()` 尚无名称透明度恢复，需要显式补充。

### 状态层

建议在独立候选核心增加只读的 `main_ready`、`sp_ready[2]` 和状态有效性信息，集中复用现有装填队列规则。不要在 Lua 再实现一份不同的冷却算法，也不要通过初始化武器来获取 HUD 状态。

- MSL 和当前载入的 SP：读取当前游戏线程中的真实状态，判断原生可发射窗口里是否已有一发就绪。不能只检查总弹药、`loadedCount` 或任意物理挂点。
- 未激活 SP：使用核心保存的队列、计时和捕获时间，按 `GetTimeSeconds` 推进允许装填的窗口；暂停时不推进。这是逻辑就绪预测，因为当前游戏没有同时实例化两个 SP。
- 切换后：以重建后的真实状态接替预测。现有核心会让已到阈值的计时在下一次原生更新中完成，以生成真实弹体；HUD 不能抢先把预测完成当作当前可发射。
- 多联导弹、负计时起点、零时长、持续发射武器：复用核心验证规则，不随意加提前完成的容差。PLSL、TLS、RKT、MGP 等特殊武器的“至少一发就绪”语义还需分别核对，不能外推成全部支持。

现有反射接口材料尚未证明存在能一次返回三组就绪状态的 getter；`package.loadlib` 桥接函数当前也没有返回 Lua 状态表。实施前需要落实核心与 Lua 的轻量传递接口，优先内存交付。此接口是后续开发工作，不是本轮已经可调用的现成功能。

如果仅做弹药耗尽变暗，可以只改 Lua；但这不足以满足本次完整需求。完整功能预计涉及 `native_hud.lua`、`main.lua` 与独立候选核心，正式 DLL 保持受保护基线。

## 性能判断

建议复用当前 10 Hz HUD 周期，一次采样覆盖三个武器。正常周期不重新扫描控件树、不创建新控件、不重排布局、不启动额外渲染层，不持续写诊断日志，也不重复执行兵装初始化。

核心每组槽数组现有上限为 64；即使三个组都遍历上限，也只是每次至多 192 个槽、每秒约 1920 次简单状态判断。这仅说明算法规模小，不是耗时测量；还要计入内存校验与桥接开销。文字设置最多涉及三个名称，状态不变时无新增透明度写入。

预期主要风险是传递方式：若每 100 毫秒调用当前完整 `native("snapshot")`，会增加文件写入、原子替换、JSON 解析和重复捕获。尤其现有状态文件默认使用持久化写入，不能把这条路径的性能说成已经无影响。应先落实轻量接口，再评价实际耗时。

10 Hz 轮询通常带来约 0～100 毫秒的状态显示延迟，游戏卡顿时可能更长。切换和恢复可在现有事务结束时立即刷新；若后续实玩认为发射后提示过慢，再研究明确的发射通知，不默认增加每帧全量查询。

## 后续实玩核对

后续候选需由用户核对：MSL 只发一枚仍保持正常、全部可用弹耗尽后变淡、第一枚装填完成即恢复、零弹药持续变淡，以及 HVAA/UGB 分别独立显示。随后核对未激活 SP 冷却、暂停、反复切换、补给换装、检查点恢复、HUD 开关与任务退出。特殊武器按种类补充，不把旧武器核心实测当作本功能通过。

性能需在相同任务、视角和设置下对比功能开关，关注帧时间尖峰与桥接耗时；本轮没有自动运行任何测试。
