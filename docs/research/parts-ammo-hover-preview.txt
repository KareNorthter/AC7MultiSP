PART 页悬停增弹与黄色数字：原生研究及三 SP 接入方案
日期：2026-10-15
适用：Steam build 9855922；codex/three-sp-research
原始记录状态：仅研究与方案，未修改模组、未编译、未安装、未运行测试模块。
后续实施：codex/three-sp-ui-polish 已在 .7 基线上实现只读预览候选，见 ui-polish-batch.txt。
下面保留当时的证据与方案；不把后续源码完成倒写为原始现场已验证。

一、结论

可以沿用原生机制实现，且不必临时装备部件或改变实际弹药。
原生把“已装部件修正”和“光标候选修正”分开计算，再为每种武器生成预览数量。
同一个计算函数还返回候选修正是否作用于当前武器；UI 据此改变弹药数字颜色及泛光设置。
三 SP 模组已有计算已装部件弹药的桥接，只缺候选上下文、预览标记和数字样式同步。
推荐保留 MSL 的原生显示路径，仅为模组新增的 SP1/SP2/SP3 弹药数字接入同一预览算法。
当前仍未实现此功能，下面的接口名称与流程是建议，不是已经存在的新接口。

二、本轮证据与验证范围

1. 离线资源
只读解析了 HangarAircraftBoardWeaponsAmmo、HangarAircraftWeaponsNameAmmo、CampaignHangarParts
及 UIManagerActor。弹药汇总包含 WeaponsMSSL、WeaponsSP1、WeaponsGUN、WeaponsFLR，
每行的名称 WeaponsName 和数量 WeaponsAmmo 是两个独立 TextBlock。
这些弹药资源没有自身的蓝图计算函数或 WidgetAnimation；不能把性能条的 BlinkBarC 动画套用过来。

2. 运行时程序分析
用户启动游戏并停留在 PART 页后，只读取得当前进程的反射信息和程序指令。
磁盘 EXE 对应位置的字节与既有运行时函数签名不一致，因此没有用磁盘反汇编结果作结论；
后续地址和调用链均来自本次运行时指令及既有已核对接口。
没有调用游戏函数、注入代码、模拟按键或替用户安装/卸下部件。

3. 用户悬停样本
用户将光标停在 Take off weight augmentation (SP.W) Lv.1，并反馈 SP 数字没有变黄。
只读记录确认：候选 PartsID=107，光标索引=47，107 不在当前六个已装部件中。
原生弹药源控件当时的文字为 MSL=126、SP1=68、FLR=3、GUN=---；数量颜色仍为标准蓝。
该现场加载着现有模组，原生 SP 源控件被隐藏、模组另画数字。
因此这个样本确认了“未装备的候选存在、现有模组未呈现其预览”，不是关闭模组后的原生 A/B 验证。
用户随后离开 PART 页，本轮停止读取页面，不要求用户为研究继续停留。

4. 尚未现场验证
未做普通导弹增弹部件的悬停/移开对照，未确认所有容量满、同组替换、卸件、不可安装分支。
没有改变模组运行代码去验证新 UI。文中的原生逻辑结论与未来方案不可当作三 SP 功能实测通过。

三、原生如何知道光标停在哪个部件

本 build 的 CommonHangarPartsWidget 派生页包含原生列表索引及部件 ID 数组。
静态路径 0x6cf850 / 0x6cf890 读取页面 +0x2f0 的光标索引，检查 +0x4e8 的数量，
再从 +0x4e0 的数组取 PartsID，写入当前候选状态。现场读得的 ID 与 107 号部件相符。
这里必须用部件 ID，不能用界面显示顺序或英文名称识别部件。

更适合模组读取的是原生已经形成的 HangarStatus 预览快照：
页面的 HangarStatus 是反射对象属性；其 BoardWeaponsAmmo 是弹药显示控制对象。
BoardWeaponsAmmo 的原生上下文访问器 0x8df100 转发到所属 HangarStatus；
HangarStatus 访问器 0x8df120 返回自身 +0x4c 的上下文。
绘制代码使用该上下文的机体、SP 选择、候选部件、部件列表和数量。
经绘制代码核对的关键相对位置如下（这是研究布局，不是公开稳定 API）：
  +0x00：机体编号；+0x04：SP 选择信息。
  +0x0c：候选 PartsID。
  +0x10：最多八个部件 ID；+0x30：有效数量。
  +0x34：更新判断涉及的状态字节，不能未经核实扩展为所有场景的有效性标记。

建议在原生状态更新后复制这份快照，而不是独立轮询键盘推算光标。
更不要把全局候选 ID 当作唯一来源：它可能属于旧页面，无法单独证明机体、世界及列表仍匹配。
现场页面会重建，本轮曾遇到旧对象地址失效；实现必须随页面代次重新绑定，不保存跨页裸指针。

四、原生如何计算“还没装备”的弹药

核心绘制函数 RVA 0x6efd90 的参数包括目标 UI、上述上下文和显示模式。
BoardWeaponsAmmo 更新路径 0x6ec5c0 将 PART 相关模式传入绘制函数。
绘制函数中可以直接看到两个独立的 64 字节修正结构：
  A：遍历上下文中的已装列表，逐个累计部件修正。
  B：仅在相应预览模式且候选尚未出现在已装列表时，累计该候选的修正。
这一已装检测避免把同一部件重复加一次。

新增发现：0x84e770 是按单个 PartsID 累计弹药修正的入口。
它调用部件表查找 0x4f7770，检查数据有效性，遍历参数及加算/倍率类型，写入传入的修正结构。
已有桥接使用的 0x84e050 则从 GameInstance 的已装部件列表累计修正。
两者用途不同：已有接口只有已装方案，不能自然产生悬停预览。

最终二者都交给现有的 0x84dc40：
  输入：真实 WeaponID、基础完整载量的局部副本、A、B。
  输出：修正后的数量；返回值：B 是否含当前武器适用的非默认弹药修正。
算法先按 WeaponID 选择适用类别，再合并倍率和加数，进行原生整数截断，
适用的特定武器类别还执行原生偶数修正。不要在 Lua 中简化成统一“增加 N 发”。

特别注意：返回值不等于“数字变大”。
它由候选的加数/倍率是否作用于该武器决定，并非比较计算前后的整数。
三等分后，某些细小增益可能被取整吃掉，显示数字不变但候选确实适用。
如果目标是尽量遵循原生，应保留这个影响标记，不自行改成“新数字 > 旧数字”。
若以后希望只在最终数字变化时变黄，应把它作为明确的产品选择，而不是误认为原生规则如此。

五、原生如何把数字变黄

在 MSL 分支，0x6f0c69 调用弹药计算并保存其返回值。
0x6f0d1f～0x6f0d90 随后根据此值：
  无候选影响：使用 TextColorStandard，开启全局泛光继承。
  有候选影响：使用 TextColorOnCursor，关闭全局泛光继承，设置 TextGlowOnCursor。
SP 分支在 0x6f15d8 调用同一计算，并在 0x6f16d0～0x6f172d 执行对应样式切换。
这里操作的是弹药数量控件，不需要把武器名称也染黄。

样式来自当前 UIManagerActor.HangarColorParameters，不应硬编码 RGB。
本轮读到的颜色值为线性 RGBA：
  TextColorStandard ≈ (0.401978, 0.651406, 1, 1)。
  TextColorOnCursor ≈ (0.760525, 0.520996, 0.012983, 1)。
  TextGlowOnCursor = (0, 0, 0, 0.2)。
所以“有局部泛光设置”已经确认，但本机该字段不是强黄色泛光。
用户感受到的亮边还可能受文字渲染及全局后处理影响，不能把它写成已证实的黄色脉冲动画。
推荐直接读取并复用这组三个样式值。不要错用 TextColorValueOver，后者并非本调用链使用的颜色。
不额外加入闪烁：弹药数字预览与性能条的黄色闪烁是两套效果。

六、现有模组为什么没有这个效果

main.lua 的 optionsFor 目前只调用 dualsp_loadout_ammo，返回三种武器已装部件后的完整载量。
该桥接调用 0x84e050，并把第二组修正初始化为空；因此从未传入光标候选。
native_loadout.lua 的 PART 刷新约每 0.25 秒重新读取已装方案，不读取悬停部件。
paintColumns 的内容签名只包含武器与数量，且没有候选影响标记或黄色样式更新。
新增的 SP 弹药 TextBlock 初始化为模组蓝色；它不是随原控件变化的实时镜像。
因此仅复制某一刻原生数字颜色、或只缩短刷新间隔，都不能完整解决这个问题。

七、推荐的三 SP 接入方案（尚未实现）

1. 只读捕获原生预览上下文
新增专用查询桥接，例如 dualsp_parts_ammo_preview。
限定单人 PART 页、当前机体/世界、有效页面代次和正确原生状态。
优先在原生 PART 状态/弹药更新完成后读取；原有定时刷新应与预览走同一展示入口，
不能在下一次刷新时又用已装数量覆盖有效的候选预览。
若以后选择轮询，应只读已绑定对象，不反复全局扫描；快照携带完整身份字段，不复用过期候选。

2. 统一计算当前值和预览值
从同一有效快照构建 A；候选满足原生模式及未装条件时，用 0x84e770 构建 B。
对每个实际已选 SP，以其真实武器类 WeaponID 和基础载量分别调用 0x84dc40。
一次令 B 为空得到当前值，一次带 B 得到预览值；两次数量都从基础载量开始，避免重复应用 A。
沿用原生武器类别、部件表、整数及偶数规则，不把原版表复制成固定清单。
这也避免把同一 SP 增弹部件错误地作用于炸弹、激光或不适用的特殊武器。

3. 最后应用 1/2/3 SP 均分
先得到部件后的完整载量，再调用项目已有 Profile.ammo 按当前真实搭载数量均分。
悬停部件不能改变槽数；EMPTY 不参与分母、不显示预览，不因尚未装备而生成第四种方案。
说明算例（不是现场实测）：某适用武器完整载量 68，候选增加 8，则完整预览为 76；
三挂显示 22→25，双挂 34→38，单挂 68→76。MSL 不参与 SP 均分。

4. 只更新数量控件的样式
每槽返回 current_ammo、preview_ammo、candidate_affects，以及快照身份和候选 ID。
PART 页有效预览时显示 preview_ammo；仅受影响槽使用原生 TextColorOnCursor/局部泛光设置。
不受影响槽、EMPTY 及没有候选时恢复标准颜色和原有泛光策略。
刷新签名加入候选/影响标记，不能只比较数字，否则数字因取整不变时会漏掉颜色变化。
用户移开、切换页签、确认装备、取消、换机或离页时结束预览；候选样式不能带到 STANDBY/HUD。

5. MSL 保持原生所有权
当前模组的弹药区平移保留了原生 MSL 行，并未为 MSL 新建第二套计算。
优先让原生数量、颜色和泛光继续更新，不要再同时写同一数字。
后续需做一次 MSL 悬停实测，确认容器移动没有破坏原生更新；若存在问题，先修复其所有权/刷新路径。
不因 SP 需要重绘就把 MSL 也全部接管。

6. 不改变实际配装和出击数据
悬停只产生局部显示快照，不写 GameInstance 已装数组、profiles.json、Flow 草稿或任务弹药。
不调用装备、保存、InitializeWeaponSystem，也不借助先装后卸来获取预览。
确认装备仍由游戏执行，模组随后重新读取已装结果，清除黄色候选状态。
部件满槽、同组替换和卸件的快照含义尚需逐项核实；不要擅自把所有预览都解释为“A 加 B”。

八、实现前仍需核实的边界与检查清单

• 普通导弹增弹部件：原生 MSL 的数值、黄色及移开恢复；SP 不应全部跟着变黄。
• 107 号 SP 增弹部件：单/双/三挂各槽的适用性、先加部件后均分以及原生整数规则。
• 同一已装部件重新悬停：不重复加成；原生已装检测与模组结果一致。
• 无关、未购买、超容量、同组冲突部件：按原生实际预览语义处理，不根据文字颜色猜可装性。
• 替换与卸件：核实上下文列表是否已排除待替换项，以及候选影响标记的含义。
• 候选有效但三等分数字不变：确认是否遵循原生影响标记显示黄色。
• 快速移光标、切分类、离页返回、换机：不得残留旧候选颜色或错误机体的数量。
• 全局泛光和手动语言：数字颜色从当前原生样式读取，不硬编码英文、RGB 或部件名。
• 第三方机体/武器/部件表：继续以实际 WeaponID 和加载后的表为依据，不扩大兼容承诺。
