# 机体故障隔离与恢复测试指导

本指导用于检查机体异常后的提示、F6诊断、原生退让、换机恢复和严重故障保护。实现边界见[架构](architecture.md#机体故障退让与f6诊断未发布源码)，总体要求见[开发规范](../project/workflow.md#故障隔离与恢复)。

## 当前可执行范围

来源为`codex/feat-aircraft-fault-recovery`的`733aa35`，本轮已接入`codex/integrate-2.26.2-alpha2`。2.26.2 alpha2保留alpha1视角、HUD和IEWS修订，并接入90资源的外挂机体方案；不能用已发布2.26.1代替本候选验收。

本轮按作者授权构建常规候选与独立开发故障候选，实际路径、摘要和环境准备结果以交付回执为准。只有显式使用`--development-fault-tests`构建且candidate=true时，才编入配置读取入口；常规包不读取故障配置，正式版拒绝该构建选项。开发包默认关闭注入。尚未由AI执行实机用例，不能把入口齐备或编译通过当作测试通过。

## 本轮操作入口

本机测试目录为`E:/AC7_MultiSP/Temp/tasks/20261028-aircraft-fault-testing/`。先安装其中入口指向的开发故障测试EXE，再运行“00_关闭注入”进行正常基线。目标机采用当前实际目录中的F-16C，对照机为Mirage 2000-5；编号写入本轮session.json，不在工具源码固定。每轮完整退出后双击对应T/U脚本，再由作者正常启动游戏；脚本不启动游戏。

T1/T2和T3三项在核心的同一资料检查器中修改读取副本或行列表，实际UE资料、PAK和兵装不变。T3重复兵装使用目标机专用的测试别名，避免同代号波及其他机体。T4在目标机原生选装接入边界返回受控异常；T5在已配置多SP后的下一次轮切事务写入前返回受控异常。T6先以选装异常触发收尾，再在一次真实所有权收尾边界报告失败，未完成的实际责任由既有严重错误收尾继续承担。T7在已配置后的轮切中从核心共享故障记录边界注入，随后由原有运行许可检查报告进程级故障。

U-current、U-newer、U-failed、U-unpublished向更新服务提供受控响应或传输失败，继续经过原有解析、后台完成和提示流程；不改网络设置。U-newer中的2.26.3只是开发响应，不是已发布版本，不点击开发响应的下载入口。每轮检查自动/手动触发方式；关闭启动检查后，自动请求应停止，手动请求仍可完成。

“保存本轮日志”在完整退出后复制轮转日志、当前状态和用例信息到results下的新目录；结果初始为未填写。“恢复测试前环境”恢复已校验的安装快照及原机体组，并保留测试期间文件。若希望测试后继续用alpha2，先关闭注入，再运行常规alpha2安装EXE；若要原样回到测试前alpha1，则运行恢复入口。用例选择和恢复工具见[离线控制脚本](../../src/research/aircraft_fault_test_control.py)。

已有离线检查的用途见[检查入口](../../tests/README.md)。这些检查不能代替F6输入、真实暂停、原生兵装及换机后的实机结果。

## 测试前准备

1. 核对候选来源提交、构建标识、核心DLL、UI DLL和Lua摘要，确保成套；保护旧冻结DLL，不覆盖旧交付目录。
2. 退出游戏后保存当前安装、个人配置和A/B分组状态的恢复副本，记录实际启用PAK及摘要。原包、存档和现有组库不作故障原料。
3. 选择两架已知正常的机体，分别记为目标机和对照机。先用原版非DLC机体验证通用控制流程；具体机体编号从本次目录取得，不硬编码此前机器的编号。
4. 测试第三方机体前，按AGENTS查询作者页面、适用版本、特殊SP、长按和皮肤功能；页面不可访问时先停止该机体测试并求助。
5. 每轮只改变一个条件，完整退出游戏后切换PAK或注入方案。不同时启用A/B组来制造故障，也不修改游戏全局网络设置来模拟更新失败。
6. 证据放`Temp/tasks/日期-aircraft-fault-testing/`，记录游戏PID、时间、注入项目、目标机体、截图及当次日志。日志有轮转，结束后及时保存完整目录，不只截错误一行。

F6诊断模式当前不主动取得原生暂停。任务内查看时先使用游戏原生暂停；关闭F6后保留原生暂停属于预期，不应由本Mod强行解除。出现无法操控、暂停无法归还或严重故障提示时，不继续飞行，保留记录后结束本轮。

## 正常流程基线

无注入、无已知异常的候选先检查以下项目；已有目录异常时，先记录真实结果，不把异常按钮存在本身判为回归。

| 项目 | 操作 | 通过条件 |
|---|---|---|
| 加载提示 | 启动至安全单人菜单 | 显示实际版本和已保存管理快捷键，持续约3秒；不抢输入、不暂停 |
| 快捷键 | 改为一个有效自定义组合键、保存并重启 | 加载提示和实际打开F6使用同一绑定 |
| 更新结果 | 分别核对最新、新版、失败和未发布结果；特殊结果需受控响应入口 | 最终结果单独播放约3秒，不把等待状态并入加载提示；不自动下载 |
| 关闭自动更新 | 保存关闭选项、完整重启 | 不自动发起更新请求；手动检查仍可用 |
| 资料正常 | 查看第一页 | 无资料异常时不显示异常按钮，也不显示异常通知 |
| 正常出击 | 目标机和对照机依次选择多SP、起飞、切换、退出 | F6与原生菜单正常，兵装数量、装填和输入无明显回归 |
| 模式边界 | 进入多人菜单再返回单人菜单，不加入在线对局 | 多人入口不接管或显示F6；返回已确认的单人环境后恢复许可，严重故障不因此解锁 |

计时以画面实际显示为准，截图不能证明持续时间；后台或加载阶段尚不可见时，不从进程启动时间开始计时。

## 人工故障用例

故障注入只能进入开发候选，默认关闭，每次启动指定一个用例和一架目标机，触发一次并在日志标明。正式包不包含可开启的注入入口，不把注入选项写入普通玩家配置。

资料故障改送入同一检查器的只读资料副本，实际机体和兵装资源保持原样；运行故障在指定阶段主动返回失败或抛出受控错误。不得改引擎指针、破坏对象内存、伪造成功清理或故意制造崩溃。只改最终异常列表、隔离标记或直接调用弹窗，不能算验证了检查与隔离流程。

| 编号 | 制造方法 | 必须观察的结果 |
|---|---|---|
| T1 缺失兵装 | 仅在目标机的检查输入中，将一槽代号替换为明确不存在的测试代号 | 产生一项异常，包含正确机体、槽位和代号；目标机退让，对照机不受影响 |
| T2 多项异常 | 同一目标机两槽分别引用不同不存在的代号 | 两项均出现；异常数按错误条目计，不因第一项失败漏掉第二项 |
| T3 重复和无效资料 | 分轮提供重复兵装代号、无效基础载量及重复机体编号的检查输入 | 对应原因正确；重复身份不任选一条放行，不误伤无关编号 |
| T4 选装错误 | 目标机选装适配执行中触发一次受控异常 | 停止该机体增强功能，保留F6和具体原因；清理成功后原生选择可继续 |
| T5 任务内错误 | 在多SP已配置后、下一次事务写入前触发一次受控异常 | 停止后续增强动作，提示退出任务；不宣称当前兵装已完整恢复原生 |
| T6 清理失败 | 在既有清理回报边界返回失败，保留真实清理责任 | 升级为严重错误，提示重启；不循环初始化或反复清理；F6在已确认单人环境可读 |
| T7 共享状态故障 | 从已有核心进程级故障报告边界注入受控失败 | 与真实核心严重故障走同一路径；普通换机和保存设置不能解除 |

T3各项分开运行。T6/T7仅验证错误传播和保护状态，不等同于真实引用泄漏、引擎加载断言或对象销毁异常已经验证。

### 普通错误后的恢复检查

T1至T5每轮继续执行以下步骤，不能只看见弹窗就结束：

1. 在目标机上打开F6，查看原因；有资料异常时进入第一页详情窗口，再关闭详情和F6。
2. 改变一个不涉及兵装重建的设置并保存，确认可以收到结果，但目标机隔离不被解除。
3. 资料检查阶段、尚未修改兵装的异常，可尝试原生单SP选择和使用；任务内T5错误先退出任务，不将继续飞行作为通过条件。
4. 退出任务，在任务外菜单选对照机，重新选择多SP并出击，确认重新准入和切换正常。
5. 选回目标机，确认本次游戏仍停用增强，不反复刷相同提示；再换对照机仍可恢复。
6. 完整退出，关闭注入，用相同候选和安装重新启动；确认人为异常消失。真实资料问题未修复时，重启后再次报告属于预期。

### 严重错误后的保护检查

T6/T7触发后，核对重启提示、F6错误详情及日志。返回菜单、换对照机、保存设置或切换总开关，都不能恢复增强功能。完整退出并关闭注入后重启，才重新判断资格。

严重故障后无法确认单人环境时，界面可能暂不显示；进入可确认的单人菜单后再检查。加载器、UI DLL或脚本初始化本身失败，仍可能没有F6，此项属于未完成的独立诊断兜底，不能用普通故障用例冒充覆盖。

## 检查输入与状态残留

每轮检查原生菜单能否返回、键鼠和手柄能否继续操作，有没有残留暂停、光标锁定、持续射击、声音不停止或自动重放旧选择。普通错误不应改变存档、购买记录、总开关及已保存组合。

在退出当前任务的前提下，F6可见和新机体可恢复是两个独立验收点。原生单SP正常也不能证明多SP恢复；必须实际选择两种或三种SP并确认可切换。

中英文各检查一次；异常详情应能滚动，按钮在关闭Mod总开关后仍可访问。只退出F6不应绕过隔离，警告不应持续刷屏。

## 真实兼容问题的对照方法

针对LMCM等资料缺失，先按[兼容性归因记录](../research/mod-aircraft-compatibility.md#本机txt说明与兵装资料缺失的归因)核对前置与实际加载表，避免把所有问题都归咎于机体间冲突。

1. 保留问题安装的文件清单和当次完整日志。记录缺失代号、机体编号、游戏PID及核心版本；目录里有记录不等于机体资源已安装。
2. 另备可恢复的精简对照安装：目标机体、作者要求的同套前置和候选3SP。其他条件保持一致，不在用户现有安装上直接散删文件。
3. 先确认检查器能否找到兵装资料，再分别观察原生单SP和多SP。原生可发射不能证明资料表完整，多SP报错也不能证明模型文件缺失。
4. 若精简组合正常，按已记录的包组逐步恢复；出现问题后缩小到具体包及同路径资源。每次变化退出游戏，保留前后摘要和日志。
5. 做一次反向确认：只撤回可疑包或换回匹配的前置后恢复，再恢复同一可疑组合后复现。只有内容、版本和实际覆盖关系能对应起来，才给该组合下根因结论。

不能把“安装了某机体后出现”直接等同于该机体有错，也不能凭PAK文件名推断最终采用哪份表。实际表来源尚无法确认时，结论保留为目录不匹配待定位。

## 结果记录与通过标准

每个用例单独记录以下内容，结果填“通过、失败、受阻、未执行”，不要预填通过：

| 字段 | 记录内容 |
|---|---|
| 来源与环境 | 源码提交、候选标识、核心/UI/Lua摘要、游戏版本、语言、管理快捷键 |
| 安装 | A/B或其他组合、目标和对照机体、相关前置版本、启用包清单 |
| 注入 | 用例编号、目标编号、阶段、是否确认只触发一次 |
| 提示与诊断 | 通知内容和时间、F6可用、详情正确、保存设置结果 |
| 游玩与恢复 | 原生流程、退出任务、对照机多SP、重选目标机、重启后结果 |
| 证据与结论 | PID、日志目录、截图/录像、残留问题、结果及未覆盖项 |

日志重点关联`LOG_SESSION`、`MOD_AIRCRAFT_ROW_UNAVAILABLE`、`MOD_AIRCRAFT_NATIVE_FALLBACK`、`RUNTIME_MODE`和`RECOVERY_RESTART_REQUIRED`。日志关键字只能辅助确认阶段，不能代替实际输入、选装和出击结果。

完成后退出游戏，恢复此前保存的安装和分组状态，核对目标文件摘要与注入已关闭。需要移走临时文件时保留证据；清理按项目规则送回收站。
