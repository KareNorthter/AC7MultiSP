# 多 SP 武器挂载设计经验

适用于 AC7MultiSP 的机体挂载适配。正式实测实例为 Steam build 9855922 的原版 F-15E、F-35C、Su-30SM；其余 44 架的离线研究已覆盖全部七组合。全 47 架的接入顺序见[全机型接入总表](#全机型接入总表)；不能直接照搬挂点编号或动画通道。

优先保留原生发射、装填和动画行为，再安排弹体与挂架。物理弹位不少于装填窗口，是改善齐射观感的目标；遇到发射路径穿插、活动挂架冲突或缺少导轨时，应接受较少的位置。F-15E 的换位、F-35C 的两处 4AAM 和 Su-30SM 的共用导轨，体现了不同机体需要不同取舍。

## 审美准则与逐机方案摘要

早期方案优先把多类模型同时显示出来，部分双挂直接沿用三挂分区，留下腹部空位、单侧某一种弹和大弹偏外的问题。少显示QAAM/UAV还暴露了把待发窗口当成外观总量的错误。用户这些调整的共同意图是：让负载看起来像一套合理、充足、协调的真实挂载。

| 设计项目 | 今后的默认做法 | 这轮吸取的经验 |
|---|---|---|
| 内外顺序 | 按实际长宽体积和支撑安排，大弹优先内翼/腹部，小弹优先外翼 | Su-30M2的4AGM腹2＋4AAM翼4；MiG-29A的LAGM内2 |
| 对称与平衡 | 双挂优先两侧成对；三挂空间不足时保持整体平衡，较大的弹仍成对靠内 | MiG-29A三挂内LAGM2，外左HPAA1/右4AAM1；不把左右分种作为统一默认 |
| 七种组合 | 单挂保持原生观感，三种双挂和三挂分别设计；少一种武器就重新分配释放的位置 | Su-35S双挂能增加腹6AAM，不必受含LASM三挂限制 |

逐机提交前，先列四种多挂各自的数量、内外/左右、原生支撑、实际离架、机构和接受的取舍，再实现资源和运行映射。用前/侧/俯视判断整体轮廓，用全LOD几何与离架方向核细节；不能只看AABB、只证明能加载或等用户逐架指出少弹。后续仍需真实游戏观感复测，不把离线几何当成主观完美或完整验收。

## 先分清几种数量和对象

| 概念 | 通俗解释 | 设计时注意什么 |
|---|---|---|
| 库存 | 这类武器还剩多少发 | 挂载模型不能凭空增加弹药 |
| 逻辑弹位 | 原生兵装队列里的位置，记录轮转顺序、装填等状态 | 不等于飞机表面独立的位置；减少外观位置不必缩短队列 |
| 装填窗口 | 当前队列里能够参与待发、补装的那一段 | 窗口内仍可能有正在冷却的弹；窗口数量不等于此刻就绪数量 |
| 物理弹位 | 弹体显示、实际离架采用的空间位置 | 可以让多个逻辑弹位轮流使用，但显示和发射必须使用同一映射 |
| 模型池 | 游戏预先准备的一组挂载组件 | 池中存在的模型不必全部显示，也不代表全部可同时发射 |
| 网格 Mesh | 组成弹体、挂架或导轨外形的三维几何 | 一块网格可能包含好几支挂架，不能默认每支都能单独隐藏 |
| 组件与挂点 Socket | 组件承载网格；挂点规定它相对父物体的位置和朝向 | 最终位置还受父链、骨骼及动画影响；网格本身不等于挂点 |

“轮转使用”是原生队列依次取弹、把已用位置纳入后续补装，再继续使用队列。mod 保存各 SP 的队列身份和顺序，把这些逻辑位置映射到各自的物理位置；它没有为每份库存创建一枚独立的外挂模型。

例如 F-35C 的 8AGM 有十二个逻辑位置、八个装填窗口，可以按库存展示十二枚；这不使它变成十二发同时待射。SOD 共存时的 4AAM 则保留六个逻辑位置、四个窗口，共用两处实际位置。

在这三架原版机体中，原生资源已经准备了三组 SP 挂架和弹体组件，通常只呈现当前选择的那组。多 SP 共存复用这些组件，依据所选武器集合、真实库存和装填状态，分别决定挂架与弹体显隐，再把真实离架位置映射到同一套组件。各 SP 的库存和冷却由兵装层独立保存，模型层负责外观与取位。

因此，把三组模型全部强行显示只是起点：重叠的挂架需要共用或隐藏，活动舱门需要继续运动，发射后还要留下正确空位。原生切换也会重新发出显隐请求，接管期间需记录这些请求，退出时归还，不能只在初始化时显示一次。

后续布局优先遵循用户明确偏好：在原生支撑和净空允许时，大体积武器放内侧、较小武器放外侧。必须按Socket实际坐标和所属载体核对，不按编号猜内外；固定巢体、炮体与共舱约束需单独评审，不能为套用大小规则而重叠挂架或修改弹道。F-2A的LASM+HVAA双挂已按此调整，含RKT三挂外侧被巢体占用，保留原分侧内翼。

## 当前三机型的布局

以下数字描述布局容量。任务中的实际可见数量还取决于库存、就绪和补装状态；“候选位置”不表示始终挂满。单 SP 也沿用当前模型显隐管理，不能把单挂视为无需核对的旁路。

`SWP1/2/3` 是机体资源中的三组模型，不是用户选装页面的 SP1/2/3。`spXX` 必须结合所属组理解，例如 F-15E 的 `SWP2.sp31` 是炸弹位置，`SWP3.sp31` 是 TLS 发射点。左右位置应看实际坐标和朝向，不能只按编号或“内外侧”的文字猜测。

### F-15E

原生逻辑数量为 6AAM 六、SFFS 十二、TLS 一，装填窗口分别为六、二、一。

| 组合 | 当前布局 |
|---|---|
| 6AAM | 原生六处 `SWP1.sp11–16` |
| SFFS | 原生十二处 `SWP2.sp21–32`，按库存显示 |
| TLS | 原生固定炮体和发射点 |
| 6AAM + SFFS | 6AAM 保留外翼 `SWP1.sp11/12`，另四处用 `SWP2.sp21/22/25/26`；SFFS 使用内侧 `SWP2.sp27–32` 六处 |
| 6AAM + TLS | 6AAM 原生六处，TLS 原位 |
| SFFS + TLS | SFFS 原生十二处，TLS 原位 |
| 6AAM + SFFS + TLS | 同双挂换位方案，另保留 TLS 原位 |

6AAM 与 SFFS 共存时的安排可以简化为：

```text
外翼：原生 6AAM 两处
炸弹外排：前、后两对改放 6AAM，中间一对留空
炸弹内排：保留六处 SFFS
原机腹四处 6AAM：隐藏，实际离架也改从上述外排发生
```

最初仅给 6AAM 腾出位置，仍让机腹导弹从原位下落，会穿过 SFFS。修订后让四枚导弹和六枚炸弹交换所用位置，保留导弹原生的下落发射行为。用户最新反馈为“几乎不会和 SFFS 穿模”，支持保留这一布局。

实现复用现成组件和 Socket：把外排四个炸弹组件的网格换成导弹网格，并让真实离架取位指向同一组件。外排中间一对不用来放导弹，以免同侧前后弹体过密。SFFS 十二个逻辑位置轮流映射到内侧六处，原生两个窗口、锁定、齐射和冷却均不变。

TLS 炮体属于挂架网格，发射点组件本身没有弹体网格。不能套用“耗尽就隐藏弹体”的规则把整座炮体藏掉；光束是否持续属于另一套生命周期。

### F-35C

原生逻辑数量为 SOD 二、8AGM 十二、4AAM 六，装填窗口分别为二、八、四。

| 组合 | 当前布局 |
|---|---|
| SOD | 原生两处 `SWP1.sp11/12` |
| 8AGM | 原生十二处 `SWP3.sp31–42`，按库存显示 |
| 4AAM | 原生六个候选 `SWP2.sp21–26`，按四个装填窗口显示待发弹 |
| SOD + 8AGM | SOD 两处，8AGM 十二处 |
| SOD + 4AAM | SOD 两处，4AAM 仅使用 `SWP2.sp25/26` 两处 |
| 8AGM + 4AAM | 8AGM 十二处，4AAM 保留原生六个候选和四个窗口 |
| SOD + 8AGM + 4AAM | SOD 两处、8AGM 十二处、4AAM 仅 `SWP2.sp25/26` |

十二处 8AGM 恢复了原生库存外观，用户明确认可，应保留。此前只显示八处，是把装填窗口误当成了全部可见模型的上限。

SOD 共存时曾尝试让 4AAM 使用 `sp21/22、sp25/26` 四处，使位置数达到四个窗口。新增两处却会与发射中的 SOD 穿插，因此恢复两处。此时允许四个窗口轮流共用两处离架位置；齐射时并不保证每发都有独立的模型消失。这是为保留动态净空而接受的取舍。

SWP2 是活动骨架挂架，必须保留原父链、Socket 和更新过程。动画推进后再取实时世界位置，才能让导弹从画面上的挂架离开。静态摆放正确，只说明某一姿态正确。

### 发射路径比静止间距更重要

检查范围要覆盖挂载、开舱、挂架伸出、离架、下落或点火、补装和收拢。F-15E 的问题出现在导弹下落途中，F-35C 的问题出现在 SOD 发射时，单看满挂截图都可能漏掉。

坐标和包围盒适合筛选候选布局。包围盒包含几何外的空白，小范围相交未必是弹体穿插；某一姿态不相交，也不能证明整个动作有足够空间。最终以真实动作和多个观察角度判断。

### 优先调整物理映射，保留原生兵装队列

本次所谓“减少弹位”，实际减少的是可见和离架位置，没有缩短逻辑队列，也没有改变窗口、锁定数、齐射数或冷却。这样能把外观安排与武器功能分开，避免为美观引入装填和轮转问题。

有空间时优先让每个待发窗口拥有独立位置；空间或资源不支持时，明确接受共用位置。不要为凑数量修改武器飞行参数，也不要机械地把所有逻辑序号取余映射到若干位置：必须核对轮转和齐射过程中是否重复占位、是否使用了正确的原始序号。

### 备用模型必须跟随真实库存和装填

8AGM 十二枚、单 QAAM 四枚，以及 SFFS 的库存外观，都可以超过装填窗口数量。但发射后必须保留空位，补装完成才能恢复相应显示；不能把备用库存直接当成已经就绪的新弹。

原生补装窗口会随队列移动，需要回溯它替代的已发射位置，避免模型立即在别处补回。多个逻辑槽共用一个物理位置时，只要其中仍有真实就绪弹，该位置可能继续可见；这种聚合结果要与逐发独立消失区分。

### 弹体 挂架和动画一起安排

选择位置时同时确认弹体朝向、导轨贴合、整块挂架的显隐粒度，以及父骨架的运动。优先复用经过核对的原生组件；确有收益才引入网格替换或新增资产。F-15E 的换位有明确动态收益，Su-30SM 的外移则需要额外资源支持才可能完整成立。

F-35C 的原生动画同时涉及舱门通道和挂架骨骼。游戏按当前 SP 驱动相关通道，非当前通道可能停止推进；非当前挂架本身也可能停更。修补时必须让完整原生动画继续运行，补齐非当前通道收拢及骨架更新，并同步原生选择编号。同舱切换保留开合进度，不能靠永久开舱或冻结骨骼绕过问题。

F-35C是新三机性能修订的参照。它保留原生父链、Socket及动画，原生Parts每帧只执行一次，之后仅补少量独立/组合通道进度；所需SWP2继续更新，发射取实时挂点。2.8.0新三机额外在Parts前后重复维护所有所需挂架并重放整组显隐，Su-47还逐组件发布重复搜索反射字段、复核全架姿态。这些重复工作已由源码确认；用户反馈F-35C正常、新三机约1–7fps，但尚无各项耗时占比，不能把模型数量或某一条检查单独定为根因。

可复用的是少量补齐和按变化处理：绑定时解析完整身份与元数据，运行时复核已绑定身份/父链；原生请求同步记账，周期维护仅兜底；同舱切SP保留开合进度。F-35C实际使用独立通道模式6，新三机当前为公共模式1，不能照搬地址、通道值或把公共进度锁为全开。Su-47旧借位还依赖已实采的严格全开姿态，其逐骨门槛不能仅为提帧率直接删除；左SAAM、右UGB/QAAM的新布局需配套分区挂架依据。用户允许轻微SP间穿模，不等于接受弹体贯穿空导轨。

Su-47左右分区已在研究分支形成`9cefa43`：三挂为左SAAM `SWP1.sp11`、右内UGB `SWP2.sp24`、右外QAAM `SWP3.sp32`，七组合设计齐全。未裁整架会扫过空导轨，需要SWP1左半、SWP2右半、SWP3右半三份派生Mesh；各原架实际只有1 LOD。离线删半面集可清除指定样本的新增接触并保留原生支撑，但尚未编码、加载或实玩，新方案暂缓注册。完整配方仍在该研究分支，取用入口见[主管工作线程](development.md#具体工作线程)，主树运行数据暂保留旧方案。

F-22A分舱逐骨依据见[舱域核对](../evidence/sp-bay-domains.json)：Body腹舱9骨、SWP3腹部15骨与侧部14骨现同读spwc；Body另10根misc普通导弹舱门不是8AAM机构。最小资源方向为专用BoneConfig表加Body/SWP3两个AnimBP副本，腹部改读swcc、侧部改读swc3，保留原Mesh/Sequence/Socket及非目标行。改表本身不能建立独立输出，安全写端与旧舱收尾尚未完成；公共原生发射门控不改。TG四个静态点则实在共舱盖板上方，三配置应共享进度，不能按组件静态推断外置。F-35C独立通道的逐帧补齐还解释了其早期快照恢复为何不能直接作为公共模式的时序保证；后移恢复是候选边界修正，尚未定位重复开合的全部最终写端。

### 预览和任务共享布局 分开保存状态

机库预览回答“这个方案看起来如何”，任务状态回答“还剩多少弹、哪里正在装填、下一发从哪里离架”。两者复用位置规则，但预览不能改写任务库存、冷却或检查点。

先确定当前显示的是机库展示机、任务玩家本体还是独立演出替身，再绑定组件。补给期间仅暂停周期刷新不足以解除旧显隐接管；同一组组件必须有明确的显示管理者。换机、组件重建、补给交接、检查点、关闭模型或失败时，都要重新校验身份并归还原生状态。

网格替换使用引擎接口，保存原网格；显隐和动画归还保留最近原生请求。一个组件归还失败不阻断其他组件，失效对象不继续访问。视觉失败独立回退，不把已成功的换装事务改报失败。实现细节见[架构](architecture.md#挂载约束)。

## 研究新机体的步骤

1. **建立原生基线。** 确认可选 SP、购买限制、真实武器类，以及消耗型、固定炮体或持续效果的差异；保留每种单 SP 的原生模型与动作记录。
2. **列出资源和运行对象。** 分别登记逻辑数量、装填窗口、模型池、Socket 的位置朝向、父链、挂架网格拆分粒度、骨架与舱门通道。资源名中的弹种数字不能替代真实武器类判断，例如 6AAM 可以复用名称含 4AAM 的弹体网格。
3. **安排组合。** 三种均可多挂时列出三单、三双、一组三挂；受单挂限制的武器保留限制。按武器集合定义布局，用户改变槽位顺序不应改变同一组合的摆放。
4. **先筛选空间。** 同时画出弹体、导轨和活动范围；以实际坐标统一“内外侧”描述。先尝试原生位置与共用支架，再评估换网格或新增资源的成本。
5. **统一显示和离架。** 同一映射用于任务显隐、真实发射和预览；活动挂点使用实时世界变换。保留逻辑队列身份，核对轮转和装填空位。
6. **分阶段验证动作。** 先单挂，再双挂，再三挂；每次只改变能独立判断的一项。外置消耗弹适合先做，活动弹舱和持续武器需要分别研究，不能因为模型能显示就开放全部行为。
7. **核对场景交接。** 覆盖原生出击与补给、菜单切页、模型组件重建、检查点和失败归还。快捷轮切用于加速观察，不能代替这些原生流程。
8. **记录结论再推广。** 将最终布局、接受的取舍和用户反馈写入本页；坐标快照、原始截图与采样回执按需留作证据。每机保留一份有效结论，不再建立相似的状态页和交接文档。

### 每架机体应核对的场景

| 方面 | 重点观察 |
|---|---|
| 组合 | 七种组合；同一集合的不同选装顺序；模型开关前后 |
| 弹药 | 满库存、低库存、最后一发、耗尽；逐发、部分锁定、满齐射；未激活 SP 的补装 |
| 动作 | 开门中、全开、离架、下落或点火、补装、关门中切换；MSL 与各 SP 互切 |
| 场景 | 选装与返回、STANDBY/PART/SKIN、起飞交接、暂停、补给确认或取消、重试检查点、重启任务、换机 |
| 恢复与性能 | 组件重建、失效身份和独立视觉回退；连续快速切换及相同镜头路径下的帧时间 |

新机体记录可直接使用以下字段，在本页增加对应机型小节：原生武器与数量、模型池与挂架、七组合映射、动画和持续效果、舍弃方案及原因、已确认反馈、仍待核对的边界。F-22A 等机型必须重新取证，不能套用 F-35C 的偏移、骨架或动画通道。

## SP 切换动画的静态研究

以下为初次筛查依据；F-22A、Su-47、Su-57 Top Gun的后续几何布局结论由下方“带动画机体的完整七组合候选”覆盖。候选已随0c13178合入主工作区源码，运行接线尚未完成；不能将旧布局阻塞或新离线候选分别误写为当前已运行状态。

2.7.0已合入以下设计、策略和分析资料。它们没有新增可安装机型；运行入口、支撑与动态净空条件仍未满足，保持原生回退。


研究分支 `codex/sp-switch-animation-research` 从 main／v2.4.0 建立，基于线程 `01a1441b-45a7-7d91-80f2-cf03b98647b1` 的全机型挂载成果继续。这里只补齐动画依据与交接设计，不更改正式三机布局，也不替代上游整机七组合准入。机器数据见[静态研究回执](../evidence/sp-switch-animation-research.json)，逐机设计见[动画策略](../src/research/sp_switch_animation_policies.json)，可复用分析入口见[开发说明](development.md#sp-切换动画研究的取用)。

### 筛查范围与确定事实

逐一读取47架官方Pawn的**实际** `PartsAnimationParamDataTable` 引用和三组SWP组件；没有凭机型名拼参数表。16架有活动骨架SWP，共29个组件。再核对这些机体本体与挂架，另包含6架仅命中SP配置标志的机体，共分析49份不同动画序列、51次组件绑定；每份101帧。逐轨解释全部压缩骨骼数据并核对属性／压缩区的骨骼映射、偏移边界、数据覆盖和四元数；非骨骼浮点曲线仅留数量／摘要，没有解释其效果。

六架“仅配置标志”的机体为F-14A、F-14A Top Gun、F/A-18E、F/A-18E Top Gun、MiG-29A、MiG-35D：三个SWP均静态，实际Body骨架没有映射到 `spwc/swcc/swc1/2/3` 的骨骼。Top Gun两型分别复用F-14A、F/A-18E的真实参数表及Body动画，不能根据配置标志就新增活动舱门管理。其余25架没有命中上述配置／组件筛查条件；这不是全游戏实机动作验收。

序列格式参照 [UEViewer 的原始序列解析实现](https://github.com/gildor2/UEViewer/blob/master/Unreal/UnrealMesh/UnAnim4.cpp)，本分析器只实现本批实际使用的ConstantKeyLerp、未压缩平移、Float96NoW旋转、无缩放轨格式，遇到其他格式直接拒绝。资源原件及完整采样不提交；回执保存官方PAK路径、加密／解码资源对和解析文件摘要。

### 可直接采用的控制设计

1. 同一动画域跨SP切换时，保存开合请求、状态、连续进度和域身份；同步兵装重建后，仍为同一机体／引擎实例才在 `keepArmed` 前恢复。保持原生选装编号指向新武器，不换AnimClass、不重新建立动画实例。关闭中、打开中、全开都不能因换槽回到起点。
2. 不同域切换，新域处理自身原生请求，旧域按原生速率收尾；EML蓄能、TLS／IEWS持续效果先按真实武器类决定能否收拢。不能把新SP的公共 `spwc` 无条件喂给所有挂架。多个组件同名但需要不同值时，须在已核对的逐组件动画求值入口路由；目前没有新增该运行入口。
3. 每帧完整原生PartsAnimation只运行一次。保留的非当前骨架必须继续必要更新；不能冻结骨骼、永久开舱，或以发射点固定为由停掉炮体。动画和世界变换更新后，显示与真实离架读取同一Socket位置／旋转映射。
4. 机库、补给、任务分别绑定世界、机体、激活器和组件索引／序列号。换世界、组件重建、关闭或失败时归还最新原生请求；失效身份不再访问。视觉失败独立回退，不能改变弹药事务成功状态。

复核旧F-35C只读采样的完整区段摘要和函数入口后，确认 `0x1ce6d70` 中公共进度按原生选择编号仅写相应分通道：0→`180/194/190`，1→`184/18c/194`，2→`188/18c/190`，其他分通道没有在这里自动收拢。它提供“为何需要非当前通道维护”的代码依据，不提供其他机体／展示实例的运行地址证明。磁盘EXE该位置仍为加壳字节，本轮分析使用已核对摘要的旧采样，没有访问游戏进程。

### 七组合交付边界

回执的 `layout_overlay` 将15架新增活动机体的七组合逐项关联到上述动画设计，共105条；F-35C另作为既有参考。保留上游选位、所属组及阻塞类别，不把条件选位改写成已解决布局。新增运行准入仍为零：共用导轨、骨架网格呈现粒度、弹体／盖板扫掠、固定武器生命周期及运行身份条件尚未全部满足。遵守参考线程“整机七组合齐全才接入”，不单独启用其中某条组合。

本轮已完成离线数据解析、摘要核对和设计落地；没有编译、新增／运行测试、安装、改动产品运行代码或操作游戏。原生帧长度、Socket原点轨迹和动画曲线一致性均不等于实机动态净空验证。

## 带动画机体的完整七组合候选

本批深入核对 YF-23、Su-47、普通 Su-57、Su-57 Top Gun、F-22A、FB-22、DarkStar、ADF-01，共8架。**F-22A、Su-47、Su-57 Top Gun形成三架21种完整离线方案**，三种单挂均直通原生；各机七行表替换下方第三批同机型旧表。这是旧完整舱内方案的范围；普通Su-57、DarkStar、ADF-01后续改为机外保留路线，YF-23/FB-22仍后置。机器数据以[mount-expansion-animated.json](../evidence/mount-expansion-animated.json)为动画覆盖层，优先于旧第三批对应机体的布局暂缓记录。旧批次仍保留原始依据，不直接改成已运行适配。

吸收动画线程`01a14787-e328-72b3-9b0e-1bfa7d81cc52`的序列解析与限定共舱控制源码（控制提交`00bd24c`，序列资料`e519d02`），新增完整骨架几何读取及逐机蒙皮核对。实际读取25份机体／挂架网格、49个LOD、326096个顶点；各活动序列取101个开合采样键。骨骼按名字及父链绑定，不能按数组序号硬对。三角面穿入与原生同一武器的接触面作比较；包围盒重叠只是筛查，零穿入也不能单独证明导轨支撑、飞行净空或运行性能。

### 接入时必须区分三种身份

`owner_group`是武器原本所属组，保留它的真实类、弹体、队列、库存、窗口和持续效果；`provider_group`是借用的真实Socket组件；`rendered_rack_groups`是唯一实际显示的完整挂架。它们可能不同。显示模型与真实发射都必须读取同一个provider在当帧动画更新后的世界变换。借位只改物理映射，不能拿另一种武器较小的模型冒充，也不能新造Socket、改父链或猜未序列化的旋转／缩放。

需要更新的骨架集合取“provider与呈现架的并集”，再筛出实际骨架组件，与选中的SP集合分开。例如F-22A只选QAAM＋XSDB也要更新SWP3；Su-47显示SWP3时仍可能取隐藏SWP2的Socket；Su-57TG的SWP3是静态组件，不读骨架字段。只隐藏组件自身，避免递归隐藏借位弹体。

### 动画控制与安全归还

[共舱控制头](../src/common_bay_animation.hpp)按机体真实网格、Skeleton、AnimClass与场景身份限定接入；切换前保存原生舱门请求、状态及连续进度，原生重建后在`keepArmed`前恢复，原生选装编号仍指新武器。原生Parts每帧完整更新一次，不永久开舱、不冻结骨骼、不替换原生曲线。TG切入第三原生配置走`NativeTransition`旁路，此时Body舱门仍需按原生流程及固定provider方案核对，不能把“无需活动挂架”写成“无需舱门”。

[native_common_bay_parts.hpp](../src/native_common_bay_parts.hpp)从PlayerPlane包装链定位原生引擎与Parts，以Steam build 9855922的九处原始代码指纹、owner回指、配置和实例身份限制访问。引擎／Parts不是UObject，不能套UObject索引校验。写入先预检，部分失败在同一身份下尽力归还并准确报告；不改配置编号、不回滚弹药事务。[owned_bone_refresh.hpp](../src/owned_bone_refresh.hpp)从实际反射元数据解析具名的骨骼刷新模式，保存并归还最新原生请求；隐藏／屏外provider不能只开Tick而不刷新骨骼。

Su-47的借位SAAM在收舱段仍与Body接触，因此只将**受管舱内弹体**设为“真实原生全开且当帧Socket匹配资源全开端点后才显示”；一开始关闭、旧帧或校验失败即隐藏。门、导轨和机体照常显示，原生发射门控不变。资源第87／100键不是Parts进度0.87，不能拿自造计时器代替。全开判据与当帧端点姿态见证必须同时成立；这是明确的可视取舍，不代表闭舱时弹体实体全程无接触。后续F-22A运行取证及原生分支核对已修正共用判据：request为1（打开推进请求仍保持）或2，且phase=2、public progress=1；request=3须立即隐藏。

F-22A现场反射还确认`bNoSkeletonUpdate`为mask2、`bPauseAnims`为mask4，不能沿用旧“mask2为Pause”的命名。非当前挂架被原生停止的是骨骼更新，开Tick不足以覆盖这项状态；接管与归还须分别保存NoSkeletonUpdate、Pause和实际Tick请求，仅按本次原生写入字段更新记录，不能从已强制后的值反推原生意图。旧F-35C清mask2的运行行为原样保留，本轮没有将其直接改写成mask4。运行依据见[采样摘要](../evidence/animated-runtime-f22a-capture.json)。

控制头是供后续线程接入的源码候选，完整产品Host、反射Socket取位、实际实例与调度仍待实现／核对，不能把资格布尔值直接填true。包含YF-23的控制profile也不代表该机几何获准。新增布局没有编译、运行测试、安装、资源生成或操作游戏；不会自动扩展运行白名单。

## 当前结论和验证范围

用户本轮认可当前挂载成果：F-15E 的 6AAM 下落段与 SFFS 穿插几乎不再出现；F-35C 和 Su-30SM 恢复原有布局更合理；F-35C 的十二处 8AGM 值得保留。这是后续研究采用的三机型参考方案。

反馈未逐项覆盖所有任务、低库存、补给、检查点、故障归还和长期性能，随后用户又确认2.4.0全部改动及两支线成果正常，包含ADFX-01持续效果；正式基线为v2.4.0。该统一反馈未提供故障注入和逐任务明细。机库转镜头掉帧在实验模型开关两种状态下均有报告，根因仍待对照确认。

### 交给整合线程的要求

首批现有F-16C、F-2A、Mirage、Rafale四机完整七组合，共28条。整合线程应同时读取位置和`rack_plan.carriers`，不能只抄Socket或只装副本。F-104C与Gripen保持整机暂缓，已有的部分分区解法也不单独启用。

1. **先核对运行对象。** 用真实类、字段反射、对象身份和模型池逐项登记。不照搬三架旧机的字段偏移、数组长度或池顺序。特别是 Gripen 七个资源 Socket、F-104C GRKT 十四个管口、F-2A RKT 七十六个管口，均不能直接当成逻辑队列长度。原资源 Sockets 顺序也不能代替运行时组件顺序。
2. **扩展容量与角色。** 当前实现有十二槽顺序表、二十处物理表、整型显隐掩码和限定槽数恢复逻辑；未核对真实需要前，不能靠扩大一个常量解决。普通弹体、固定巢体和逐管发射位置应分别管理，火箭巢不随单发消耗或库存耗尽被整座隐藏。
3. **按完整几何拆架。** JSON 中给出应保留的区域和 Socket，不包含生成后的游戏资产。拆分需核对三角面索引、所有 LOD、材质与边界，保留原挂点元数据；不能仅按顶点 Y 值删点，或把单 section 误当成单支挂架。登记新旧网格身份，用引擎接口替换，候选变化、单多切换、关闭模型和失败时归还。
4. **再确定逻辑映射。** 保留原生槽身份及冷却，按最终物理位置定义映射并核对所有轮转游标；不能直接根据表中少数位置推导已验证的一一齐射方案。预览、模型显隐、真实离架共用同一规则，低库存与装填空位单独观察。
5. **整机交付实测。** 先确认一机七组合均有方案，再实现并交付整机；内部可依次核对单挂、双挂、三挂，但不能交付半套适配。没有分区依据或仍有其他组合受阻的飞机整体后置，不把视觉依赖写成 SP 功能互斥。全部动作观察仍按前文场景清单执行。

研究数据中的 `physical_count_unit` 区分普通站位与火箭管口；火箭另列 `launcher_body_count` 和 `muzzle_count`，不能按管口数量创建同等数量的可见巢体。运行逻辑槽数和模型池容量尚未核对的字段均留空。

可复用工具为 [catalog_native_mounts.py](../src/research/catalog_native_mounts.py) 和 [build_external_mount_plan.py](../src/research/build_external_mount_plan.py)。前者从原版索引及提取清单生成机体目录并核对来源；后者读取显式 manifest，合并人工几何评审，检查七组合覆盖与 Socket 引用后生成研究数据。已交付批次 JSON 本身也可作为后者的 `--decisions` 输入，重新提取后不依赖临时评审文件。输出须选择新文件。临时解码资源留在研究工作区 Temp，不放入 Git 或交付包。它们属于离线资料工具，不是测试模块或安装入口。


### 已核对静态分区的接入约定

本轮复用技术线程的静态退化索引法：保留区域三角面不动，排除区域变成零面积面；覆盖主索引、反向、深度、反向深度与邻接缓冲的全部LOD。它保留顶点、材质、Socket及原包围范围，不能视为减顶点或性能优化；只证明离线结构能写出和回读。

使用独立`/Game/AC7MultiSP/Research/MSP_...`包路径，不覆盖原版资源。加载须在确认的游戏线程边界完成，核对StaticMesh身份并持有引擎管理引用；路径变化后按新文件名重新编码并生成新回执。当前工作区没有复制技术线程Temp中的游戏资产，也没有打PAK。

副本只能装到其原所属组；同几何不等于同Socket元数据。共用可见挂架时，另一组保留原网格和取位组件，仅隐藏架自身，不能递归隐藏子弹体。资源替换只在绑定或集合变化时进行，稳定帧不重复加载或换网格；单挂、关闭、失败及场景交接归还原网格和最新原生显隐后再释放引用。

退化面不会自动改碰撞、导航或烘焙光照。原BodySetup、NavCollision和LightingGuid仍在，接入前必须确认外观挂架为NoCollision且无相应烘焙依赖；条件不符就停止该机接入，另做资源处理。火箭巢还有独立装置生命周期，不能套普通弹体逐发显隐。十四条分区候选的`runtime_prerequisites`均记录这些前提；原生逻辑长度与物理映射仍须按真实槽身份完成。

资源实验工具[split_static_mount_asset.py](../src/research/split_static_mount_asset.py)、[批量实验入口](../src/research/run_static_mount_split_experiment.py)与回执一起原样引入，供后续专用资源工作复现；本轮未运行它们。方案生成使用[build_static_split_mount_plan.py](../src/research/build_static_split_mount_plan.py)，核对副本来源、所属组、保留区域、配方哈希及全部LOD往返依据；它只输出JSON方案。

### 第二批接入时特别注意

先按`integration_gate.eligible`整机过滤：只有七组合齐全的飞机可进入运行接入。其后才读`disposition`区分原生参考、资源复用和技术阻塞；一架暂缓的飞机，即使某条为`candidate_existing_assets`也不单独实现。暂缓不增加SP功能互斥。

原生 Socket 不遵循统一的逐组顺序编号：例如 F-4E 的 SWP1 可到 sp22，F-15 S/MTD 的 SWP2 使用 sp31/32，火箭还会使用三位数管口名。当前三机实现的顺序命名检查、固定容量和限定槽数恢复，均不能直接外推。Typhoon 的十八个 8AGM 候选加两类腹部点还会超过现有二十处物理表，须先核对实际运行池与队列，再确定接入结构。

表中“隐藏整架”是隐藏其网格外观，保留组件、原父链和 Socket 取位；不能销毁组件、停止必要更新或连带隐藏仍需显示的子弹体。微小占位网格也不等于机体本身的支撑已经检查完毕。应与对应原生单挂画面对照确认导轨和机体净空。

静态闭合间距不能替代动作观察。重点包括 F-15J 前后导弹、F-16XL 窄间距 UGB、Typhoon 前腹 HCAA 与内侧 8AGM，以及 FAEB 展开。FAEB 已同时读取闭合与展开网格，保守分侧没有改动原生投放或空爆参数；实际时序仍待游戏验证。原生备用模型数量、低库存、装填空位、补给和检查点也没有在本轮验证。

### 后续动画与资源专题的顺序

当前已有十机静态路线及三机动画路线完整七组合。以下仅为暂缓飞机的后续研究顺序，必须解决其全部组合后才整机接入。若专门扩展动画，可优先查看 F/A-18F 的 QAAM／LASM＋EML、Su-33 的 HVAA／LASM＋EML、ASF-X 的 6AAM＋LASM、F/A-18F Block III 的 LACM／8AGM＋4AAM，以及普通 Su-57 的 4AAM＋PLSL。这八种在本批 B 组主要受动画控制阻塞，数据含 `required_animation_work`；不是已证实要拆架，也不是本轮可直接接入的候选。DarkStar 的 SASM＋PLSL、FALKEN 的 TLS＋翼下武器也可随后研究独立活动组。

F-22A、Su-47、Su-57TG已由产品线程接入2.8.0并安装供测试；Su-47只对完整已核全开姿态提供精确可视门槛，其他姿态仍待扩展。新版实玩反馈尚未取得。YF-23、FB-22、普通Su-57、DarkStar与ADF-01按上文具体阻塞后置；X-02S另有同舱、共位和独立EML机构问题；CFA-44 最后处理阵列、双炮与效果源。不能仅因骨名和参考姿态一致，就叠加整套活动呈现，或把一机的 spwc 修补直接套给另一机。

数据保存显式的 Socket 位置／朝向、骨骼父链、Body 与 SWP 各自 AnimBP、原生通道与序列信息；缺省字段为未知。参考姿态不代表停挂姿态，序列采样长度不代表游戏开门耗时，动画压缩数据不同也不等于每条曲线必然不同。真实释放路径、低库存、补装、切 SP 途中收拢、补给／检查点／组件重建仍须接入后观察。
