# 多 SP 挂载设计

本文记录已验收并本地发布的2.19.0、2.19.1用户反馈及已安装2.19.3候选的CFA/FALKEN策略，适用原生 Steam build 9855922。2.19炮口按地址查找修订已获用户确认有效、卡顿明显减少；2.19.1互切无展开动画也获确认，但仍明显卡顿，并有MSL/EML双发反馈。后续`codex/cfa44-fire-switch-audit`减少重复核对、修补CFA发射状态跨类别的边界，并改为FALKEN发射期间丢弃切换请求，已接收至2.19.2并成套构建、通过现有检查和安装，实际效果待用户测试。已测旧版本与产物不回改。完整旧研究和逐组合长表保留于[挂载设计归档](archive/multi-sp-mount-design-before-2.16.txt)。

当前47架有武装原版/官方 DLC 机体均有处理方向：23架常规布局、6架机外保留、2架原生外观旁路，合计31架有明确接入策略；另16架后置。31是策略覆盖数量，不代表31架七组合、所有任务与检查点均已实测。无武装 `f104av` 不在此47架范围内。

2.17反馈：CFA的ECM模型不再显示，切ECM时ADMM/EML展开可以接受；2.18切换仍明显卡顿。用户要求仔细研究，若没有显著优化方法应直接建议放弃。2.16已知ADF-01停光卡顿、F-22A准备页光标短卡、F-2A多挂性能仍单列观察，不能从总体反馈推定已解决。

| 对称与平衡 | 双挂优先两侧成对；三挂空间不足时维持整体平衡 | MiG-29A 内LAGM2，外左HPAA1/右4AAM1；不把左右分种当统一模板 |
| 七种组合 | 三种单挂、三种双挂和三挂分别设计；少一种武器后重新利用空位 | 不能把三挂的半侧分区直接套到所有双挂 |

## 已验证经验与踩坑

- **CFA已验证有效**：2.19将炮口记录改为按地址定位，无关显隐请求不再逐条核验历史炮口，失效清理集中到模型提交。用户确认卡顿明显减少，见[验收](../evidence/2.19.0-user-validation.json)。这证明该修订有效，不证明所有动画卡顿同因，也不代表已消除武器重建成本。
- **计时不能混算**：2.18首次约792ms、后续137–318ms是当时核心事务数据。`native_init`含模组同步回调，不等于纯引擎开销；过滤耗时是阶段总耗时的子集，不能相加。登记次数不等于存活对象数，旧数据不当作2.19的新测值。
- **ECM曾被错误收舱阻断**：旧方案在ECM期间逐帧压低公共`spwc`，使原生阶段无法达到可发射状态。外形隐藏应继续用组件/局部骨隐藏，不能用压低公共进度替代。ECM隐藏、ADMM/EML保持展开的观感已获认可；公共门槛冲突见[2.16调查](../evidence/2.16.0-performance-investigation.json)。
- **F22改善伴随功能取舍**：撤去腹部九骨显隐后用户反馈无肉眼卡顿，但当时已简化内舱外观。它支持减少高频骨操作，不证明完整内舱共存一定能同样流畅。旧完整方案及腹骨方案分别保留于`archive/full-bay-mount-2.8.1`、`archive/f22-belly-bones-2.11`。
- **TGM仍不能承诺**：2.8.1已有缓存和重复维护削减，Su-57 TGM仍获2–3fps反馈；没有足够分项证据定量归因，见[实测](../evidence/2.8.1-user-validation.json)。后续须先定位，不把CFA成果直接推广为旧全舱方案可用。
- **检查按生命周期安排**：静态资源、反射布局和代码资格优先绑定时核对；高频路径仅查目标对象与必要动态状态，同值不重复写。对象存活、地址换代、范围、发射挂点和退出恢复不可整体取消。一次同步操作可合并重复检查，不能把跨引擎调用的旧指针当成持续有效。

## 数量与映射

| 概念 | 含义 |
|---|---|
| 库存 | 剩余弹药，不由模型位置数决定 |
| 逻辑队列 | 原生每个槽的装填/冷却身份，运行时从真实 Group 读取 |
| 待发窗口 | 同时可装填或待发的数量，不一定等于模型池或锁定数 |
| 持久模型池 | 原生组件集合；资源 Socket 数只用于身份与集合核对 |
| 物理位置 | 当前布局真正使用的显示/发射点，可以少于逻辑槽或待发窗口 |
| 挂架与发射器 | 导轨、巢体、炮体、逐管口、效果源分别管理，不能都按消耗导弹隐藏 |

`SWP1/2/3` 是原生资源组，不是用户选装的 SP1/SP2/SP3；原生兵装配置是0/1/2。`spXX` 必须连同所属组解释。左右以机体坐标为准，负Y和正Y固定，不跟随观察镜头。

减位不缩减库存、窗口、锁定、齐射或冷却。多个逻辑槽可轮流共用物理点，因此少位组合不保证每次齐射都有独立模型消失。备用弹按真实库存、就绪和补装状态显示，不凭候选 Socket 总数强制挂满。CFA 原ADMM池126个发射组件、分侧选择42口，也不表示有126枚可见实体弹。

### FALKEN发射期间拒绝切换（后续修订）

用户反馈提前停光仍明显卡顿，要求改为发射完成后才能换槽。原路径包含原生End、反射布局/主束身份核对、MainLaser显隐及兵装重建；此前缓存反射元数据仍未消除用户可感知卡顿。没有分项计时证明全部由动画接管造成，也不能将CFA的炮口查找结论直接套用。

2.19.1已安装的等待方案会暂存最后一次选择。用户最新要求不保存命令，后续源码改为直接拒绝，覆盖TLS＋4AAM、TLS＋FAEB及三挂，TLS在任意逻辑槽均相同，外观功能关闭也有效：

- 发射中请求其他SP或MSL时保持当前选择和鼻口，清空待切换请求；主束及尾迹自然退场后必须重新按键，不自动切换。
- 拒绝发生在释放发射输入之前，沿用取消FALKEN强制End及反射隐藏主束的策略；不改发射时长、伤害、冷却和池回收。持续按住发射可能触发下一发，仍以实际活动状态为准。
- 请求到来时只读当前玩家两组原生武器引用，以活动位包含尾迹；不扫全局对象，不保有旧发射体，不为已丢弃请求新增轮询。普通连射仍保留原有每50ms查询及五秒超时，不与TLS拒绝策略混用。
- 原生兵装重建与必要的非当前鼻口通道收拢保留，因此不是完全取消动画控制。移除的是提前停光的同步流程；预计减少这部分切换峰值，不能保证重建后的停顿也消失。

拒绝策略的来源报告保留源码阶段记录；本轮已接收至2.19.2并成套构建、通过现有检查和安装。用户实测应区分“发射中按键被拒绝”和“自然结束后重新按键切换”两处停顿，并观察尾迹、最后一发、反复选择、切MSL及外观关闭状态。若自然结束后仍明显卡顿，需定位兵装重建，不能靠继续删检查承诺改善。

### CFA切换与ECM当前策略

- 同机、同组合、同组件资源的普通切换保留分侧骨隐藏租约，避免Init前展开、提交后再隐藏；提交时重新核对隐藏状态，只修复被重置的分支。补给重配、换机、单挂和失败退出仍完整归还。
- 原生显隐请求继续记账，相同目标位不重复调用引擎；骨架Tick/NoSkeleton归还值未变时不重复调度。CFA只展示固定架，周期维护不再为126个空发射组件捕获ADMM弹药队列和计算就绪位图，弹药、冷却及离架映射保持原实现。
- ECM用SWP3组件双显隐位及两组机构骨隐藏兜底。依据 `evidence/sp-switch-animation-research.json` 的fa44/SWP3：七骨父索引为 `[-1,0,1,1,0,4,4]`，隐藏Body直接子骨 `SWPCover_01/04`，保留Body及其 `sp31` 发射点。运行时核对网格、骨架、骨数、骨名和父链；使用原生 `HideBoneByName` 的 `PBO_None`，不改碰撞、公共开盖进度或发射阶段。
- 此策略限多挂；单ECM继续原生。机身公共舱门仍可能随原生动作打开，目标是隐藏ECM伸出机构，不能以关门阻断发射。首次反射解析及原生兵装初始化仍有成本，不宣称卡顿已消除。

2.17用户确认ECM隐藏观感可接受，切换卡顿未解决；不扩大为ECM功能及所有组合均验收。后续源码保留该外观取舍，移除任务外CFA多挂预览：Lua在加载/绑定前退出，核心mode1再次旁路，原生选装及UI不变；任务内与补给仍沿既有布局。

### 2.19.2现场：旧锁定登记残留

用户授权读取暂停中的游戏内存并手动复现。已核验17运行文件与2.19.2回执一致；先读暂停现场，再以10ms间隔只读采样。两次MSL有效按键分别扣2，批次总数为19/16；两次EML有效按键均分两步扣1+1，批次总数15。期间真实锁定槽只有0或1个处于锁定状态；SP重建后旧槽指针换代，但LockedTargets仍为16。采样到的重建池库存恢复不计为发射，轮询不是原子快照；用户确认有效发射每次都是双发。

根因是重建前只停了旧槽声音，没解除登记。原生重建直接丢弃槽数组，残留列表中的存活目标不会被原生失效过滤删除；新批次按列表项数计划发射，即使MSL/EML的fire_all仍为0，也会连续发射当前可用的两发。旧记录随着目标死亡或原生重选而减少，解释了“时有时无”和ADMM后更容易出现。批次边界修订保留，但它不能修复这种在每次新发射时重新读入的脏列表。

共用修订在每次模组重建前完整调用原生逐槽Reset，随后对旧版本无现存槽负责的登记调用原生解除通知。所有机体的出击初始化、SP换槽、调试、补给和检查点恢复均覆盖，不只CFA，也与模型开关无关；不对正常ADMM/多目标列表去重，不强制单发，不清除SelectedTarget或候选表。它只修复已经确认的共同路径，不能等同于所有机体所有双发现象都已实测消除。来源研究阶段未编译安装或写入游戏进程；本轮已接收至2.19.3成套构建、通过现有检查并安装，需用户复测正常多目标齐射、快速换槽、补给/恢复及声音配对。已有原生快照、旧假设及失败回执保留，见[现场证据](../evidence/cfa44-live-seeker-residue.json)。

## 继续适配的方法

1. 明确真实类、网格、父链、原生池和Socket，区分弹体、固定炮体、逐管口、UAV及效果源；缺资料及时报告，不按编号猜位置。
2. 分别设计三种双挂与三挂，列数量、内外/左右、真实支撑、显示/离架映射和接受的瑕疵。先用足已掌握的原生站，再评估借位。
3. 静态分区保留材质、Socket、非索引数据和全部LOD，核对主/深度/邻接边界；完成原编码字节复原、新名编码与独立解码回读。资源只留本机，不提交游戏资产或密钥。
4. 复核真实面与离架方向，AABB只作筛选；窄AABB不等于穿模，静止零穿面也不等于原生下落/延迟点火已通过。
5. 资源、源JSON、生成表和PAK同步交付；运行重新核对NoCollision、弱身份与归还账本。构建、测试、安装和游戏操作按当次授权执行。
6. 实测分别记录机库/皮肤、选装、任务、单多切换、低库存/装填、补给、检查点、开关和退出。未覆盖项明确留下，不能用“其他基本正常”替代逐项验收。
