# 开发规范

适用于人工、AI聊天和子代理。用户明确指令优先；本规范防止并行覆盖，不新增反复确认。正式状态见[项目入口](../../README.md)，资料职责见[文档索引](../README.md)。

## 开工与责任范围

1. 看实际Git状态、路径、分支、HEAD与main。发现未提交内容先核对归属，不暂存、覆盖或顺手提交。
2. 读AGENTS、README和本规范，再按索引读唯一主题正文；不把旧资料的“当前”当现状。
3. 一任务一责任线程、一分支、一工作树。在[工作区索引](workspaces.md)登记目的、责任聊天、基线、改动范围和状态；更新已有行，不另建交接文档。
4. 明确本轮授权。默认不编译、写/运行测试、安装、操作游戏、推送、上传或重建发布包。静态差异、文档链接和摘要核对不等于运行测试。
5. 资料或环境受阻，说明具体缺口并求助，不反复猜测试错。

子线程在自己的分支登记任务行，不直接并行改main的登记表；管理/整合任务按独立任务键接收登记差异。公共文件的修改范围发生变化时先更新登记，不能借“只改一行”越过另一线程的所有权。

## 分支与并行

| 用途 | 命名 | 规则 |
|---|---|---|
| 正式源码 | main | 由接收/整合任务更新；没有授权不推送 |
| 功能/修复 | codex/feat-主题、codex/fix-主题 | 从核对后的main建立，限定范围 |
| 研究 | codex/research-主题 | 保存半成品、证据和未决条件，不冒充功能完成 |
| 文档/维护 | codex/docs-主题、codex/chore-主题 | 不夹带功能或个人环境改动 |
| 接收/发布 | codex/integrate-主题、codex/release-版本 | 统一接收精确差异，整合阶段确定目标版本 |

旧名字不为格式强制重命名。恢复旧聊天先看工作区索引，原目录可能已封存。

- 不允许多个线程编辑同一工作树；只读协助可共享。编辑子代理须分文件所有权，不能同时改同一正文。
- 公共核心、生成表、版本、协议、配置迁移须单一整合责任。冲突按语义处理，不整文件覆盖，不任选一边。
- 不自动联系其他用户聊天。子代理范围和模型遵循用户授权，不自行改变任务目标。
- 研究接收只收必要差异，不把旧核心/Lua/文档整套搬回main。
- 长期分支接收前比较main变化；保留旧提交，不改写公共历史、不强推、不擅自rebase其他任务。

## 提交规范

一个提交表达一个可审阅目的。标题建议“类型: 中文动词＋对象＋结果”，例如“docs: 统一开发规范和研究索引”。类型：feat新功能、fix修复、refactor行为不变的重构、docs文档、research研究、chore维护、release经授权交付。

正文按需说明问题、最终变化、验证范围和限制，不写操作流水。

- 提交前看精确差异和暂存区，只暂存本任务明确文件；禁止默认git add .或git add -A混入其他成果。
- 源码和对应正文同次接收，新文档登记索引。纠错改现行正文，不改历史回执。
- 不提交个人配置/状态、存档、游戏素材、第三方PAK、原始转储、发布ZIP、工具或凭证；Temp/和backup/必须忽略。
- 未获验证授权写明“静态审阅，未编译/测试”，不能称通过。既有检查只对记录的源码和产物有效。
- 提交、合main、安装、用户验收、发布是不同状态，各有依据。

## 版本号与接口编号

- Mod正式版本用主版本.次版本.修订号：重大兼容变化增主版本，新增功能增次版本，修复/性能/小调整增修订号。
- 纯文档/仓库整理不增功能版本、不重建已验收字节；正式标签vX.Y.Z不移动或覆盖。
- 研究线程保持基线功能版本，用分支、提交和“未发布”条目区分，不抢占下一正式号。整合者结合全部成果确定一次目标号。
- 自测版使用`X.Y.Z alphaN`，例如`2.25.3 alpha1`；alpha表示交给用户自行测试，序号从1递增，元数据必须标记candidate。正式状态仍保留上一正式版本，待用户验收后再确定正式`X.Y.Z`，不因合并或构建完成自动转正、不倒填验收。其他候选阶段先补齐工具支持再使用，不能只改文案导致解析器误认。
- 安装器与Mod共用产品版本，程序集和manifest在封装时从VERSION生成，不再维护独立安装器版本；历史回执中的独立版本保留当时含义。
- 协议、配置和资源清单按兼容语义更新，不随Mod号机械增加。VERSION和产品元数据由整合阶段统一。
- 历史2.25/2.26等研究号按原记录保留，不重排回执，不虚构正式发布。

## 用户交互与双语

双语要求针对F6管理页面、弹窗通知、安装器等本Mod提供的交互，以及玩家文档和主页；游戏自身UI保持原样，不因该要求扩展汉化。

- 按文字所属界面和用途判断双语范围，不能仅因本Mod向原生游戏控件写入文字，就认定该文字必须汉化。未经用户明确要求，不扩大游戏自身UI的翻译范围。
- 上述Mod交互包括菜单、按钮、设置说明、提示、确认框、进度、成功/警告/错误信息、更新内容、安装说明、作者及授权文字。向用户展示的日志说明也应有双语解释。
- 新增或修改上述范围的用户可见内容时，同步维护两种语言，功能、含义、限制和操作步骤一致；不能只翻译标题，正文或错误分支仍留单一语言。
- Mod界面按所选语言显示，文档提供对应语言版本；不要求每个控件同时堆放两种文字。按钮、提示和文档使用一致术语，避免截断、乱码。
- 原生选装/补给页的指定固定标签使用英文，兵装具体描述、起飞和操作提示继续区分中英文；精确范围和维护方式只在[界面文字资源](../user/interface/README.md#原生选装与补给的语言边界)维护，不回滚共用文字资源或修改原生控件逻辑。
- 同一内容的每种语言各维护一个来源，EXE、ZIP、F6从对应来源读取或生成，不按展示位置分别改写。用户人工修改后同步更新译文。
- 机体/兵装正式名称、作者署名、邮箱、网址、路径、错误码等保留必要原样；第三方许可证保留法定原文，另提供中英文说明，不自行翻译替换原许可证。
- 只供开发者使用的源码注释、内部研究和原始诊断数据仍按项目中文规范维护。现有单语内容登记为待补齐，未补齐前不能宣称双语已完成。

接收用户交互改动时核对中英文内容是否齐全、含义是否一致；界面实际显示和语言切换按当次验证授权检查，不因本条自动获得编译或测试授权。

## 更新日志与文档

### user中文文件逐条审核

任何对`docs/user/`下中文文件的改动，包括四份中文正文、中文文字资源及其他中文文件，必须先列出每一项拟议差异及原因，由作者逐条明确审核确认后才能写入。新增、删除、改写、润色、条目重排、格式或编码调整、批量替换和自动脚本造成的变更均在范围内；不得静默修改，不能以功能调整、版本更新或同步文档的一般授权替代逐条审核。

作者自行修改并明确要求接收的中文原稿，按原字节接收、记录摘要并同步英文，不再要求作者重复审核自己的改动。发现原稿有疑点时，只提出具体建议，未经逐条确认不改原稿。英文翻译、界面生成与封装不得反向改写中文源文件；完成后核对中文原文摘要未变。

[玩家更新日志](../user/更新日志.txt)是唯一持续维护的更新正文。2.25.2之后的版本（从2.25.3起）按完整版本号分别记录具体新增、修复和调整，中英文同步，不再概括为2.25.X或其他主.次.X阶段；每个条目只写该版本实际变化，不重复前版全部内容。2.25.2及以前的历史概括保留，不倒填或改写旧发布记录。正式发布时，可按作者明确要求将自测阶段的改动整理到指定正式版本，并移除玩家日志中的alpha明细；Git及历史证据、旧包和回执原样保留。2.26.0按本次作者要求汇总2.25系列至alpha5的主要改动，后续仍逐正式版本记录，不恢复系列概括。玩家正文不写内部研究编号和技术流水。研发依据留Git、evidence及唯一对应的工程正文；[开发版本旧记录](../archive/development-history.md)只供查证，停止追加。四份玩家正文的分工和跨界面复用见[玩家文档维护](player-docs.md)。

- 未接收成果写“未发布”或研究索引。资料不足的早期阶段只标中间研究版本，不补造变化。
- README维护现状和入口；AGENTS维护约束；架构写当前机制；开发说明写路径/依赖和恢复；工程经验写关键结论；回执保留当时事实。
- 玩家文档独立为功能说明、安装说明、主要更新、作者与授权四个主题，中英文必须成套；EXE、ZIP、F6从同源读取或生成，不各写一份。F6文档只展示主要更新和作者与授权。
- 章节失效就合并重写或归档，不能只在顶部加“以下为历史”，留下多个竞争的“当前”。
- 研究记录写问题、证据、结论边界、未决事项、源码/原料位置和继续条件；移除重复对话及无意义流水，保留关键失败原因。
- 历史全文以Git标签恢复，不为每次整理复制整套。未提交原件另存核对快照；原始用户要求和第三方许可证不能用摘要替代。
- 文档可多，但每份必须有用途、唯一维护来源和索引入口；已有合适正文优先更新，不新建“交接/最终总结”副本。

## 接收、验证与交付

涉及新版发布时按[新版发布流程](release-workflow.md)执行，协议与包结构分别见[主页说明](pages-site.md)及[交付方案](delivery.md)。R2、蓝奏云、Nexus通用ZIP及Pages上传由作者手动完成。玩家正文和作者信息继续同源，固定主页文字进interface双语资源；生成目录、上传ZIP、远端部署、客户端联网分别记录。历史上传包不回写，不用旧包内正文覆盖当前main。

接收至少给出来源分支/提交、差异范围、依赖、验证状态、未决事项。整合者确认没有回退其他成果，再合对应源码和正文；提交标题“完成”不是证据。

代码验证、游戏实测、发布仍按当次授权。冻结源码、构建、安装、用户验收和发布分别记录，不能互相冒用。当前交付方式见[交付方案](delivery.md)，不为适配旧脚本保留重复或错误文案。

## 结束与清理

状态统一：进行中、待接收、待验证、已接收、封存待续、已关闭。更新工作区/研究索引原行即可。

清理分支前核对：提交已被main包含或差异接收已确认；无人写入；未提交/未跟踪内容已保留；ignored原料和冻结依赖已查明。重要tip先保归档标签及引用清单，再去掉分支名。

含独有原料、未提交成果或恢复路径依赖的工作树先原位封存，不强行清空。未采用研究保留源码锚、原料和继续条件。缺目录登记先保存Git元数据；不能声称Git已恢复ignored资源。

实体清理送回收站；不自动git clean、强制清除、全仓重置或清理对象库。备份区分实际文件和链接，目录存在不代表能恢复。大资产清理另做，不与功能交付混合。

新任务文件放Temp/tasks/日期-主题/，不要散放Temp根目录。旧原料与现场先查[本机资产索引](../archive/local-assets.md)，按清单定位，不因目录名含Temp就删除。GitHub保存范围及私有仓库约定见[仓库说明](repository.md)；本机ignored资产与未提交内容不能当作已上传备份。
